# T2-4 规则与 AI 二次仲裁说明

日期：2026-10-13。依据：现行《重构方案》§4.3、《计划分工》T2-4、用户对《T2-4_阶段分析与详细计划》的逐项批注及本阶段确认。

## XML 优先顺序

同邮件已确认同票且有可靠 XML 票号来源时，跨格式匹配的发票业务字段只从 XML 来源取值；PDF、图片作为票面凭证来源，不覆盖或补填 XML 业务值。XML 缺失字段保留缺失，多 XML 冲突保留待核。

本轮同号记录去重先检查 XML：有效 20 位票号、有 XML 票号位置证据且这些 XML 记录五项必填字段一致时，直接采用首条 XML 记录。其余记录不再入 Excel，原记录仍留 JSON。不能直接选择时，先合并相同字段组合的写表候选，再检查 XML 对差异字段的证据；无法唯一确认时人工待核。有 XML 来源的未决组不转交 AI 推翻 XML。只有无 XML 来源的冲突组才进入下表的 AI 仲裁分支。完整流程见 `01 docs/02 technical-design/excel去重.txt`。

## 无 XML 来源时的判定表

下表中 AI 自动选中记录的路径仅适用于通过本地文字证据核对的纯文字仲裁。扫描件或混合页面一旦进入图片模型仲裁，最终仍保留人工待核，不按模型选择自动跳过候选。

| 本轮输入 | Excel | `task_debug.json` | 提示与状态 |
|---|---|---|---|
| 票号为空或 `Not Found` | 各自按原入表条件处理，不因共同空值去重 | 全留 | 缺失和格式校验归 T2-6；三关键字段全缺仍由主流程排除 Excel |
| 相同非空票号，五项必填字段一致 | 首次遇到的记录入表，后续相同记录直接跳过 Excel | 所有发票原记录及来源全留 | 跳过项在邮件 `error_reason` 和可定位提示中记录；不新增“重复”状态 |
| 相同非空票号，五项有差异，AI 有原文证据选中一个已有记录 | 只写所选记录 | 原始候选全留，不改写字段 | 未选记录标人工待核并给来源提示；已选记录保留原有状态 |
| 相同非空票号，五项有差异，AI 不可用、证据不足、输出第三种结果或无法确定 | 每种不同的冲突候选各写一行；完全相同的后续副本仍跳过 | 原始候选全留 | 冲突候选标人工待核并给来源提示 |

“五项”指 `invoice_date` 开票日期、`invoice_number` 发票号码、`total_amount` 报销金额、`receipt_type` 票面类型、`seller` 销售方。发票类型 `invoice_type` 是非必填；行程单关联、旅行字段、状态、来源不参与重复判定。金额用 `Decimal` 数值比较，`100.0` 与 `100.00` 属一致，不改变 JSON 保存的原精度。号码只要求非空才参与；例如两张均为 `ABC123` 仍先比较，号码格式错误留 T2-6 报告。

本轮“首次遇到”按主流程的未读 UID 顺序和每封邮件中的文件顺序；代码不读取历史 Excel 或数据库。附件字节 MD5 去重仍属 `attachment_processor.py`，和本阶段不同。

## AI 输入、提示词与结果

仅无 XML 来源且同票号的五项字段发生冲突时调用。`stage_ports.load_stage_ports(cfg)` 将本轮配置绑定给 `arbitrate_records`，主流程在 T2-3 匹配后、T2-6 校验前调用。每个冲突组联合提交候选及来源证据，不逐张调用模型判定。当前程序使用 `pdf_input.prepare_pdf` 逐页准备各来源 PDF：纯文字路径使用本轮配置的 `dashscope_model`；扫描件或混合页面将需视觉读取的页面渲染为图片，与提取文字及页码一起提交给 `dashscope_vision_model`。两条路径均使用本轮配置的 API Key。原始 PDF 文件不直接上传，视觉路径会提交渲染后的页面图片。输入限制和失败边界见[PDF 扫描件修复说明](../../PDF扫描件修复说明.md)。

请求包含：冲突组的差异字段、每个候选的 `record_id`、邮件 UID/主题/日期、发票来源文件序号与完整原名、五项当前值和来源 PDF 文字；另有 `attachment_groups`，按邮件列出该组涉及的全部附件及其中 PDF 的文字。若 PDF 准备失败或超限，本组不自动选中，直接交人工核对；需要视觉读取的页面可提交图片模型，但最终仍保留人工核对，不自动采信视觉选择。系统提示词在根目录 `prompts.txt` 的 arbitration 分区，由 `prompt_loader.py` 读取：邮件和 PDF 只作为证据；只选一个已有 `record_id`；纯文字仲裁的每个差异字段须逐字引用所选 PDF 原文；不能确定则返回 `null`；不允许造第三套字段值。

约定响应示例：

```json
{
  "selected_record_id": "Msg2-01",
  "evidence": [
    {"field": "total_amount", "quote": "价税合计 200.00 元"}
  ],
  "reason": "第二张来源文字清晰"
}
```

纯文字仲裁只用 `selected_record_id` 和 `evidence` 判定。编号须属于该冲突组；每个有差异的字段必须有一项引文，引文要能在**被选记录自己的 PDF 文本**里找到，且包含对应字段值。若另一候选的所有差异值也能从其自己的 PDF 原文找到，两份文件都各有证据，程序不让模型任选赢家，而是留给人工核对。`reason` 是模型说明，不能代替原文证据。模型返回别的编号、第三种字段值、证据缺漏/不符、PDF 无文字、接口失败或结果无法解析，均不自动选赢家，按人工待核处理。此校验可核对模型输出的结构与引文对应关系，**不能证明发票真实、PDF 完整或模型的业务判断一定正确**。“能确认其一”在本阶段指有更充分的来源文字支持某一候选，不等于验证发票真伪。

视觉仲裁虽可返回页面定位和模型判断，但当前缺少可独立核对图像内容的本地证据校验，因此保留各候选并交人工核对，不执行自动选中。模型生成的 OCR 文字不能作为独立证据；不能将“已调用图片模型”写成“已实现自动视觉仲裁”。

## 输出与实现边界

- `MailRecord.records` 始终保留所有原始发票。新增的 `excel_skip_record_ids` 是内存中的写表选择清单，`mail_to_dict()` 不把它序列化为新业务字段；主流程 `_excel_rows()` 据此跳过 Excel 新行。
- 仲裁提示进入 `stats.not_found_alerts`，同时以记录编号和差异原因追加到所属邮件 `error_reason`，以便 JSON 仍能追溯被跳过的来源。`dedup_skipped` 继续只表示附件 MD5 去重。
- 冲突未选项使用已有 `status="人工待核"`，不新增“重复”状态。上游原有待核状态不会被清除。所有原记录仍供后续 T2-6 检查；仅写 Excel 时应用跳过清单。
- XML 来源优先分支已接入；上表中的 AI 分支仅适用于无 XML 来源的冲突组。
