日期：2026-10-13。状态：T2-4 研发实现及受控自测完成；独立测试、真实 PDF/模型联调和阶段验收尚未完成。用户进一步明确二次仲裁须将各 PDF 文字放进同一请求，不逐文件分别调用模型；本实现和以下测试按此口径执行。

## 实现与规则

根目录新增 `dedup_arbitrator.py`，仍由 `stage_ports.py` 自动加载。`pipeline.run_pipeline()` 保持原公开入口，向阶段端口绑定本轮配置，使冲突时能读取来源 PDF 文本并调用当前配置的模型。`data_model.MailRecord` 增加两个仅供运行时使用、不写入 JSON 的控制字段：Excel 跳过记录编号和仲裁提示。`pipeline._excel_rows()` 只跳过确定的重复/未选记录，`_write_debug()` 继续保存每封邮件的全部原始 `records`。技术图 `01 docs/02 technical-design/excel去重.txt` 将“有效票号”更正为“非空票号”，与用户确认的 `ABC123` 相同错误号码仍需比较的规则一致。

同票号只比较五个发票必填字段。完全相同则后续记录跳过 Excel；字段冲突时，程序读取同组邮件中相关 PDF 的文字，连同全部候选和差异点一次交给 AI。AI 只能从已有记录编号中选一个，且每个差异字段须有该来源 PDF 的可核对引文。失败、无文字或第三种结果均保留不同冲突候选 Excel 行并标人工待核。JSON 全留、来源不改、原始业务字段不由 AI 改写。详细判定与输入/输出格式见《T2-4_规则与AI仲裁说明.md》。

## 给后续任务与测试方

1. T2-5 核对 `source_file_seq` 对应文件、内部落盘名和完整原名；仲裁复读 PDF 依赖这条来源链。来源 PDF 无法读出文本时不进行自动选中。
2. T2-6 对五项必填字段及有值但格式错误的号码逐条校验，包括被跳过 Excel、仍保留在 JSON 的发票。T2-4 不把 `ABC123` 判为有效号码，只把相同非空值放在同一比较集合。
3. 测试方可独立构造两封同票号邮件、文本 PDF 冲突和 AI 假响应，逐项比对 Excel 八列与 JSON 全量字段；正式标准答案应按已确认规则先制定，不能从运行输出倒推。真实模型与样本仍需专项验证。
4. 历史 Excel 不参与判重。同一输出目录跨轮复用仍可能积累历史行；项目既定要求每轮使用独立目录，T2-4 不改为历史去重。
