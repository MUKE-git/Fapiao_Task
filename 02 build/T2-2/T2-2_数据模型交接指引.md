# T2-2 数据模型交接指引

产品验收已全部通过。数据结构以根目录 `data_model.py` 为实现依据，字段规则见 `01 docs/02 technical-design/字段表.txt`；模型负责承载与序列化，不承担提取、匹配、仲裁或运行时业务校验。

## 四类实体

| 实体 | 主要数据与关系 |
|---|---|
| 邮件 MailRecord | mail_id、mail_uid、subject、mail_date；包含 files、itineraries、records、dedup_skipped、error_reason |
| 文件 FileRecord | 文件序号、物理格式、完整原名、预读结果、内部名、导出名；可保存 acquisition、source_ref、model_usage |
| 发票 InvoiceRecord | record_id、kind、fields、source、matched_itinerary、status；一张发票一笔候选记录 |
| 行程单 ItineraryRecord | record_id、match_amount、travel_time、origin_dest；可保存来源序号、冲突及交付阻断标志，不含销售方或承运企业字段 |

PDF、XML、图片进入处理链。OFD 在文件登记前忽略；数据模型中保留 OFD 枚举用于兼容测试及旧数据，不表示当前主流程处理 OFD。`ofd_processor.py` 暂保留供测试动态引用。

## 金额、空值与序列化

金额内部采用 Decimal，JSON 用十进制字符串，保留原始小数位；格式错误的输入保留供校验，不提前四舍五入两位。Excel 显示两位不改变 JSON 原值。发票金额取价税合计，行程单匹配金额独立保存，不能互相代填。

发票类型非必填，缺失为空字符串；其他字段的缺失使用既定缺失标记。旅行字段只在有值时序列化；没有匹配关系时省略 matched_itinerary。全部行程单无论匹配与否均保存在 itineraries 中。

## 来源与交付

mail_id 是本轮 Msg 序号，mail_uid 是邮箱 UID，两者不同。文件序号与 mail_id 共同定位本轮来源；JSON 保存完整原名及内部名。source 可保存字段证据、冲突、交付阻断和同票关系。exported_name 仅在来源被选中并实际交付 PDF 时填写。

## 业务边界

匹配由 itinerary_matcher.py 实现：金额层级与原名消歧、逐轮重算、符合条件时初始或末尾单对单；金额容差为 0.5，不是 0.005。同轮票号仲裁由 dedup_arbitrator.py 负责，附件 MD5 去重明细由 dedup_skipped 承载。field_validator.py 区分 a/b 类检查，b 类不检查旅行字段；行程单只校验独立保存的金额、时间与路线。

## 输出与验证

mail_to_dict 序列化邮件、文件、全部行程单和发票记录。Excel 固定八个业务列，由主流程筛选和组装后调用写表模块；三关键字段全缺和本轮重复记录可能不入表，因此 JSON 记录数不必等于 Excel 行数。

18 条必选虚构用例原有预期已人工审核；逐字段扩展草案仍待人工审核。实际运行状态见对应测试报告，产品验收通过不改变测试预期。数据结构、来源映射和文件存在均不能证明票据真伪或模型字段正确。
