## 实现及契约对应

1. `attachment_processor.py` 统一计算内部完整文件名，计入 `MsgN_文件序号_`、扩展名及重名后缀后不超过 120 个 Python 字符。超长主体截断并加原名 SHA-256 前 8 位作短摘要；同名目标已存在时顺延 `(1)`、`(2)`，每次重新计算可用长度。实际写入使用独占创建，防止并发创建同一路径时覆盖已有文件。清理 Windows 非法字符、空名和设备保留名仅作用于存盘名；完整 MIME 解码原名仍在 `FileRecord.original_name`。无名直附件可按 MIME 类型补实际扩展名；`.ofd`、`.xml` 等不再误用旧 `.pdf` 兜底。ZIP 容器存盘名也受 120 字符上限约束，但容器本身不占 `files[]` 文件序号。
2. 现有同邮件 MD5 去重与 01–99 连续编号仍由 `collect_mail_files` 负责，直接附件和 ZIP 解出文件共用一套序号；去重跳过项不占序号。`FileRecord.internal_name` 记录最终实际落盘名，`exported_name` 在 T3-1 导出前保持空值。
3. `pipeline.py::_check_source_chain` 在统一写 Excel/JSON 前检查本轮 `mail_id`、IMAP UID、邮件内文件序号、内部名唯一性和实际落盘文件存在性；检查发票及行程单记录编号、`source_file_seq`、`matched_itinerary.file_seq` 均指向同邮件登记项。目录外路径或断链会报错，不将错误来源当成成功结果写入 Excel。`task_debug.json` 的现有字段已足够从内部文件名反查唯一文件登记、邮件 UID 和相关记录，因此未增设第二套编号或来源字段。`data_model.py` 只修正一处旧注释，将“全局定位键”改为“本轮定位键”。
4. `pipeline.run_pipeline(cfg, log)`、`collect_mail_files(msg, mail, cfg)` 等现有公开入口未改签名。T2-3 原名匹配与 T2-4 按内部名复读来源 PDF 的职责不变；T3-1 的用户导出业务名及 T2-6 的差异化字段校验未提前实现。
