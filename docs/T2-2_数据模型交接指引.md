## 1. 项目背景（一句话）

这是一个**发票邮件处理系统**：通过 IMAP 收取财务邮箱里的发票/行程单邮件，识别其中的 PDF/XML/OFD/图片等凭证，提取字段（票号、金额、日期、票面类型、销售方、出行时间等），按「一发票 = 一笔」落成结构化记录，最终输出一张员工报销用的 Excel 汇总表，并对缺凭证、字段缺失、重复、人工待核等异常做分类提示。

**当前进度**：阶段一（代码拆分）已完成——原有 `invoice_pipeline.py` 已拆为 config / utils / type\_classifier / ai\_client / fallback\_extractor / excel\_writer / attachment\_processor 七个模块；你现在做的是**阶段二的核心逻辑重构**，T2-2 是其中一环。

### 1.1 关于 T2-2 与 T2-1 的完成顺序（存疑 2 澄清，重要）

> 《计划分工.md》阶段二列的依赖顺序为 **T2-1（主循环 driver） → T2-2（数据模型）**。
> 但实际推进中**把完成顺序调整为：先做 T2-2 数据模型细化 → 再回头做 T2-1 主循环重写**。

**调整原因**：

1. **数据模型是主循环的地基**。T2-1 要把主循环改成「凭证形态分流 / 一发票一笔」，它依赖 `files`/`records`/`source`/`matched_itinerary` 等结构；若结构未锁定就先写主循环，一旦模型返工，T2-1 全部白做。
2. **用真实数据先校验结构**。先把 T1 阶段遗留的 `task_debug.json`（真实邮件）按新结构重组、导出校验表，肉眼核对模型是否站得住，确认后再让 driver 按已锁定结构实现。

**对你（执行者）的意义**：你接手 T2-2 时，**T2-1 主循环尚未按新模型重写**，这正好——你先把数据模型与转换配方交付并验证，它为 T2-1 提供结构契约。**不要因为原清单写成 T2-1→T2-2 就误以为先要有一个成品 driver 才能动模型。**

| 术语      | 含义                                                                     |
| ------- | ---------------------------------------------------------------------- |
| 凭证      | 发票 / 行程单 / 通行费单等单据文件（PDF/XML/OFD/图片）                                   |
| 凭证形态分流  | 按文件类型分流处理：发票→提发票字段；行程单→提行程字段；XML/OFD→结构化提取；图片→多模态识别                    |

## 5. 数据模型契约正文（T2-2 的核心产出）

### 5.1 记录单位与粒度

- **records = 数组，一条 = 一张发票（一笔）**。
- 一封邮件可产生多条记录（含多张发票时各自成行）。
- 行程单**不单独成行**，匹配成功后把 `出行时间/出发地目的地` **汇入对应的 a 类发票行**。
- 输出 Excel 按 records 逐行写。

### 5.2 四类对象（类图）

数据模型由 4 类对象构成，关系如下：

- **邮件**：mail_id / mail_uid / subject / mail_date
- **文件**：file_seq / file_type / original_name / pre_read_type / pre_read_invoice_no / pre_read_amount
- **发票**：record_id / kind(a类·b类) / 6 业务字段(日期·号码·金额·发票类型·票面类型·销售方) / status；a 类额外汇入 出行时间/出发地目的地
- **行程单**：record_id / match_amount / carrier / travel_time / origin_dest

依赖方向：`邮件 → 文件 → (发票 | 行程单)`；`行程单 …> 发票`（匹配成功后汇入 出行时间/出发地目的地）。

### 5.3 \[JSON 基线] `task_debug.json`（每封邮件一个条目）

```json
{
  "mail_id": "Msg3",
  "mail_uid": "1747702802",
  "subject": "来源邮件主题",
  "mail_date": "YYYY-MM-DD HH:mm",
  "files": [
    {
      "file_seq": "01",
      "file_type": "PDF|XML|OFD|图片",
      "original_name": "附件原始名",
      "pre_read_type": "Invoice|Itinerary|…",
      "pre_read_invoice_no": "…",
      "pre_read_amount": "…"
    }
  ],
  "records": [
    {
      "record_id": "Msg3-01",
      "kind": "a类|b类",
      "fields": {
        "invoice_date": "YYYY-MM-DD",
        "invoice_number": "…",
        "total_amount": 1264.0,
        "invoice_type": "电子发票（普通发票）",
        "receipt_type": "客运服务|机票款|…",
        "seller": "…",
        "travel_time": "a 类由行程单汇入; b 类留空不写 Not Found",
        "origin_dest": "同上"
      },
      "source": {
        "source_file_seq": ["01"]
      },
      "matched_itinerary": {
        "file_seq": "02",
        "match_amount": 53.93
      },
      "status": "complete|缺凭证|人工待核"
    }
  ],
  "dedup_skipped": [ {"filename": "…", "reason": "…"} ],
  "error_reason": ""
}
```

要点：

- `fields` 中 **b 类不写** **`travel_time/origin_dest`（留空），不要填 Not Found**（D5）。a 类这两个字段在**行程单匹配成功后**才写入（写到 a 类发票行）。

### 5.4 来源元数据 & 文件序号（契约 §5）

- 全局定位键：`Msg{序号}-{文件序号}`，如 `Msg3-02`。
- 邮件标识 `Msg{序号}`：本轮未读邮件按序编号；内部缓存 IMAP UID 保证追源稳定。
- 文件序号 `01/02/…`：该邮件下所有参与处理的文件统一编号（PDF 直附件、ZIP 内 PDF、XML、图片、OFD 同一套，邮件内唯一），**与邮件双向可查**。
- 存盘名 `Msg{序号}_{文件序号}_{安全名}`，同名不覆盖；内容相同时只保留首份。
- 规则：任何"文件序号"必须能反查到具体邮件 + 文件，不得只有序号无关联。

### 5.5 a 类发票判定（【D4 已含"费"字容错】）

- 定义：票面类型 ∈ {通行费, 客运服务费, 代收通行费}，做**子串关键词匹配**，并对"费"字容错：
  - `客运服务` 与 `客运服务费` 均视为 a 类（哈啰开 "客运服务"、嗖嗖开 "客运服务费"，是同一类票）。
- `config.py::TRANSPORT_RECEIPT_KEYWORDS` 当前值（已含 `客运服务`，见 §3）：
  ```python
  TRANSPORT_RECEIPT_KEYWORDS = ["客运服务", "代收通行费", "运输服务费",
                                "通行费", "网约车服务费", "出租车服务费"]
  ```
- 判定方式：`any(kw in receipt_type for kw in TRANSPORT_RECEIPT_KEYWORDS)`（子串命中）。**注意保持子串匹配，不要改成全等匹配**，否则哈啰"客运服务"会被漏判成非 a 类。

### 5.6 字段归属 = 校验边界（D5）

- `出行时间 / 出发地目的地` 的**所有者是行程单**，行程单页提取；匹配成功后**汇入 a 类发票行**。方向永远是「行程单 → a类发票」。
- b 类不涉及这两个字段 → 不物化、不校验、不在 Excel 显示。

## 6. 行程单匹配逻辑（【D3 已改稿】）

适用范围：**仅 a 类发票需要**。流程：

1. **单发票 + 单行程单 → 直接成组**，无需匹配（最优先，逻辑任何复杂规则之前）。
2. 多对多时按优先级：
   - **① 报销金额**：四舍五入 ± 容差（建议 0.005）内命中；
   - **② 原文件名**：发票名与行程单名的文件名关键词对应；
   - 两级均未命中 → **人工待核**。
3. **销售方不再参与自动配对**；仅在人工待核时作为**参考线索**给用户看。
4. 命中成功 → 把 `出行时间 / 出发地目的地` 汇入 a 类发票行；`matched_itinerary` 记录 `文件序号 / 匹配金额`。

> 纠错提醒：早期方案误写"行程单匹配锚点=发票号码"，**锚点是报销金额，不是发票号码**。别写反。

## 7. 字段校验（契约 §6）+ 旧代码 3 处改动点

**职责**：消除旧代码"b 类被假报缺 出行时间/出发地"的误报；校验以**字段归属**为边界。

| 类型  | 校验字段                        | 说明                                 |
| --- | --------------------------- | ---------------------------------- |
| b 类 | 日期/号码/金额/发票类型/票面类型/销售方（6 个） | **不查** 出行时间/出发地                    |
| a 类 | 上述 6 个 + 出行时间 + 出发地目的地（8 个） | 后 2 个校验"是否已从行程单**汇入**"，不是"发票自身是否有" |
| 行程单 | 金额/销售方/出行时间/出发地目的地          | —                                  |

**旧代码改动点（3 处，均在** **`invoice_pipeline.py`）**：

1. `build_fallback_audit_result`：发票侧**去掉**抠 出行时间/出发地目的地 的逻辑。
2. `_collect_not_found_alerts`：改为**仅 a 类 + 校验汇入**。
3. `SUMMARY_COLUMNS` 写入时机：a 类三个字段在行程单匹配后才汇入。

## 11. 已知坑（与 T2-2 强相关，务必看）

1. **特殊版式（哈啰/嗖嗖类）文本层**：这类新发票 `发票号码：`、`开票日期：` 顶部是**空的**，真票号**竖排嵌在"发票监制章"内**，旁边竖排 `旅客运输服务` 字样。纯正文正则会**抓不到票号/日期**。→ 数据模型必须支持"预读票号/预读金额"字段，并在 AI 缺失时允许 `Not Found`，不要因此把整条记录判废。
   - 判别信号：文本层出现 `统一发票监\n制`、`全 章`、`旅客运输服务`、票号紧贴监制章。哈啰 `receipt_type` 是 `客运服务`（无"费"，D4 已容错）。
2. **b 类字段**：`travel_time/origin_dest` 对 b 类**留空**，别填 `Not Found`（否则用户表会被假缺字段刷屏）。
3. **排序/回归对照**：`Msg{序号}` 现为 IMAP UID，回归对照时**比业务列，不要比 Msg 数值**。
4. **旧代码历史污染**：桌面与项目输出同名目录（如 `Invoice_Task`）可能有历史数据，重跑前先清理。
5. **压缩包/去重**：ZIP/7Z/RAR 递归限 2 层、解出文件 ≤50、总大小 ≤15MB；同一邮件内容相同（MD5）的附件只保留首个，明细记 `dedup_skipped` 且**不展示给用户**。
6. **163 IMAP**：需先发网易专用 ID 命令才能 SELECT；长空闲会被掐连接（Errno 10054），要有重连；`logout()` 可能抛 `IMAP4.abort`，清理动作不得改变任务成败语义。（仅与整体流程相关，T2-2 开发若只做模型可略读。）
