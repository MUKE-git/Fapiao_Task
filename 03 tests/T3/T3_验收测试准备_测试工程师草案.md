## 1. 测试对象、证据和判定边界

- **样本文件**是测试输入；`run_pipeline`、格式处理器、前端和模型接入是被测程序；`run_fixed_cases.py` 一类脚本是测试入口；`expected.json` 是事先确认的预期；运行产生的 `task_debug.json`、Excel、日志、导出包是实际结果。五者分开归档。
- **受控测试**：用固定的单文件提取结果替换外部模型响应，实际执行邮件/附件、匹配、去重、校验和输出。它能证明后续程序在给定提取结果下的行为，不能证明真实 XML/OFD/图片识别或模型效果。
- **真实解析测试**：直接把四种样本交给真实格式处理器，检查逐字段结果、错误、来源。若只运行解析器，不能证明邮件到 Excel 的整链路。
- **整链路测试**：固定 EML、附件或受控下载响应进入真实程序，检查文件登记、逐文件提取、匹配、JSON/Excel、前端展示和用户交付物。再安排一组真实模型/邮箱/下载站联调；受控服务结果不能冒充真实外部服务通过。
- 已审核用例的标准答案继续独立于运行输出。T3 新样本的逐行逐字段预期应先由规则和可见原件制定，经产品审核后入库；不得从实际 JSON/Excel 反向生成。机器比较覆盖 JSON 与 Excel 的**全部约定业务字段**，并显式比较列映射、类型/格式、空值、记录数、来源、待核原因；区分“草案比较”和“正式验收”。

## 4. 拟增材料的实施与验收顺序

1. 先建立**输入清单**：保留用户原件在本机，记录文件 SHA-256、格式检查和人工可见字段；链接场景使用脱敏固定邮件正文与受控 HTTP 响应，不把外部站点瞬时状态写成固定标准答案。公开/共享测试材料前须脱敏真实交易、税号、链接签名等信息。
2. 根据流程图与已确认规则，分别写每个场景的**预期草案**：应产生几笔发票、每笔完整八个业务字段、空值和格式、JSON 来源文件列表、行程单列表、状态与提示、Excel 行和列、精简 ZIP 清单、PDF 业务名、前端定位信息。逐项核对 ZIP：只允许汇总表、`task_debug.json` 和 `用户票据`中的发票/行程单 PDF；XML/OFD/图片和内部目录不得进入交付物，金额缺失的 PDF 名称不得附“元”。本机/云端页面仅提供已核查 ZIP 下载，且不显示输出文件夹名、桌面路径或备份按钮。未确认的产品用语留给产品审看；测试工程师不得自称用户已确认。
3. 先做处理器真实解析（XML、OFD、图片、PDF）、再做受控整链路、最后做真实模型/真实下载联调。每类报告写明调用了什么、替换了什么、比较了什么和未覆盖什么。
4. 在现有测试入口扩展机器比较时，**复用原入口**，避免两套标准答案。先对新场景以“草案比较”运行；用户确认预期后，才将相应场景标为正式验收。全字段 JSON/Excel 自动核对要覆盖既有用例和 T3 新用例，不仅比较二者彼此一致。

## 5. 待产品审看的事项与技术处理边界

- **需产品审看**：前端提示语是否准确、清楚、礼貌；“缺凭证”和“需人工处理”的用户动作；同一记录展示多个文件来源的顺序；邮件主题、邮件时间的展示格式。测试方只制定可核对的提示场景，不替产品批准文案。
- **工程与测试自行落实**：XML/OFD 字段映射、命名与来源契约、下载链接提取及安全策略、模型供应商接口、异常重试、格式识别（包括 `.png` 实为 JPEG）、OFD 转换工具选型、用例运行方式和差异报告。若方案中的业务预期确实相互矛盾，再把具体冲突及影响交产品裁定，不以接口细节打断产品。
- **当前已知测试缺口**：已有 18 条必选用例主要是 T2/PDF 与行程单基线；没有已审核的 XML、OFD、图片、正文链接、跨格式匹配、T3 前端展示和 T3 模型真实调用标准答案。上述 T3 内容仍是测试工程师草案，不得把已有用例审核状态扩展解释为 T3 已审核或已通过。
