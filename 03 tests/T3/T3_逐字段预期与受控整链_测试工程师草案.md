# T3 逐字段预期与受控整链（测试工程师草案）

> 作者与状态：**测试工程师制作、待用户审核**。本稿及 `fixtures/xml_only_expected_draft.json` 只用于草案比较，不是正式验收标准答案。原有 18 条必选用例的编号、顺序、范围、`expected.json` 和样本均未修改。

## 事实核对

- 已审核固定库为 18 条必选、26 个变体；现有 `run_fixed_cases.py` 以固定 IMAP/EML 和预写 `extract.json` 替换 PDF 文件级提取，实跑公共附件链、T2 匹配/仲裁/校验、JSON 和 Excel。其 `expected.json` 多数只声明记录数、配对及部分字段，并非全部业务字段的逐项标准答案。
- `audit_frozen_expectations.py` 只读每个冻结 `expected.json`，报告 JSON 六个发票字段与 Excel 八列中尚未被明确比较的字段；它不读取程序实际输出，且不补写任何标准答案。
- 审计实际输出：**18 条、26 个变体、25 份发票文件级受控结果**；其中冻结 `expected.json` 对 JSON 六个发票业务字段完整逐项检查的是 **0/25**，对 Excel 八列完整逐项检查的是 **3/25**。这不是用例未审核，而是现有机器比较覆盖不足；扩展预期仍须独立制定并由用户确认。
- `compare_full_fields.py` 是通用比较器：在预期文件已写定后逐邮件、逐记录检查身份、类别、状态、完整发票字段、来源序号、全部行程单字段；Excel 检查八列顺序、行数、每个单元格和金额数值类型。差异报告精确到路径。`--mode formal` 会拒绝未标为“已由用户审核”的预期；`--mode draft` 只生成草案比较。JSON 和 Excel 分别对预期比较，互相相同不算通过。

## 先写好的仅 XML 草案

`fixtures/xml_only_synthetic.xml` 是合成输入，票号和销售方均为测试值，不是发票真伪证明。`fixtures/xml_only_expected_draft.json` 依据该输入可见字段及 PRD、重构方案的“仅 XML 形成记录、缺票面凭证、b 类不汇入行程字段、八列 Excel”规则，在运行前写定六个 JSON 字段、状态、来源以及一行 Excel 的八列值。它不从 `task_debug.json` 或 Excel 反推。

运行 `run_controlled_xml_only.py` 时：

1. **调用** `run_pipeline`。固定的合成 MIME 邮件进入实际邮件解析与公共附件登记；实际执行 T3-6 跨格式端口和 T2 仲裁、字段校验、JSON/Excel 输出。
2. **替换** 外部 IMAP 返回值和 XML 处理器的文件级返回值。XML 返回值在脚本中预先固定，且脚本检查实际收到的附件字节与输入样本相同；没有调用真实 XML 解析器、真实邮箱或百炼模型。
3. **检查** 将本轮 `task_debug.json` 和汇总表分别对预写草案逐字段比较，并报告 `run_pipeline` 错误状态。通过只能证明在给定 XML 结果下后续程序的行为；真实 XML 提取、外部链接、页面、ZIP 和用户产品验收仍须分别核查。

在本测试工程师工作树的旧接线提交 `567d4c2` 上，比较结果为 **FAIL，差异 1 项**：`json.mails[0].records[0].status` 预期“缺凭证”，实际 `complete`。这说明本基线尚未把仅 XML 状态写入 JSON；不修改草案去迁就实际值。T3-9 集成分支补完接线后需复跑，同一草案仍须用户审核，复跑 PASS 也不自动变成正式验收。

在接入 `8b19bbd` 与状态修复 `614d4ec` 后，同一受控入口复跑为 **草案比较 PASS，0 项差异**；比较器自身 3 个测试通过。该运行仍替换 XML 文件级结果与外部 IMAP，不能证明真实 XML 解析或真实服务。

## 冻结 18 条的字节级回归条件

直接在此 Windows 工作树运行原 `run_fixed_cases.py` 得到 **3/26**，其余差异均为输入清单的 SHA-256/字节数不符。以 C04/v1 的 `00_raw.eml` 核对，清单和 Git 对象均为 39968 字节、相同 SHA-256；`core.autocrlf=true` 的工作树文件为 40500 字节，换行转换导致清单核验失败。另有 C02 的清单恰与检出副本一致，因此不能笼统选择 Git 对象或检出文件。

`prepare_frozen_blob_copy.py` 只在忽略的 `03 tests/T3/result/` 建临时副本，对清单列出的每项输入分别选择 SHA-256 **及字节数都匹配**的 Git 对象或检出副本；原冻结文件、清单与预期完全不写。用这个副本调用**原封不动**的 `run_fixed_cases.py --pdf-mode controlled`，在当前集成代码上得到 **26/26 PASS**。它仍是固定文件级提取返回的受控回归，不能代替真实 PDF/AI 或 T3 全格式整链测试。清单混有不同换行版本，后续仓库维护应独立修复检出属性或归档方式，不能为让测试绿而改清单哈希。
