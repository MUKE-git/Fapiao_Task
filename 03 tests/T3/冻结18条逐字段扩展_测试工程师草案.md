# 冻结 18 条逐字段扩展（测试工程师草案）

> **测试工程师制作、待用户审核。** 本扩展草案单独保存；原固定用例库的 18 条编号、顺序、输入、`extract.json` 和 `expected.json` 均未改。草案比较通过不是正式产品验收。

## 预期来源与编制顺序

1. 以固定库 `index.json` 的 18 条必选、26 个变体及其原顺序确定范围；可选 C11 未混入。
2. 每个变体从固定 `extract.json` **受控文件级结果**抄录发票六字段和行程单三字段，从原已审核 `expected.json` 读取关联关系、入表行数及已确认的部分字段。编制脚本逐项断言两者不冲突。没有读取程序实际 `task_debug.json`、Excel 或运行报告来生成预期。
3. 根据已确认规则，匹配的 a 类发票只从原预期指定的那份行程单汇入出行时间和路线；未匹配发票的 JSON 旅行字段及 `matched_itinerary` 不出现，Excel 两列为空。行程单本身不写 Excel 行。三个主字段全部为 `Not Found` 的发票不入表；其他发票依邮件与附件来源顺序入表。该规则也与原已审核每变体的 `excel_rows` 核对。
4. 静态答案为 [`frozen_18_full_fields_draft.json`](frozen_18_full_fields_draft.json)，编制逻辑为 [`compile_frozen_field_draft.py`](compile_frozen_field_draft.py)。覆盖 26 个变体、25 份发票结果、21 份行程单结果、24 行 Excel，其中 6 个变体零行、8 个发票与行程单匹配。静态文件写定后才执行程序比较；编制脚本拒绝覆盖已存在草案。

## 比较范围与结果

[`compare_frozen_field_draft.py`](compare_frozen_field_draft.py) 先用字节数和 SHA-256 均符合冻结清单的临时输入副本，**调用未修改的** `run_fixed_cases.execute_variant` 和产品 `run_pipeline`。替换的是外部 IMAP 返回的固定 EML 以及每份 PDF 的文件级提取结果 `extract.json`；邮件解析、附件登记、记录组装、匹配、JSON 与 Excel 实际运行。原 `expected.json` 的比较照常执行，随后从同一轮产物另作草案比较。

扩展比较逐变体检查 JSON 发票六字段与匹配时的两个旅行字段、未匹配字段的缺席、全部行程单三字段、匹配对象和金额；Excel 检查八列表头与列映射、逐行八个值、金额数字类型和 `0.00` 显示格式、空值与 `Not Found`。草案结构本身还检查 18 条/26 变体顺序、记录数、字段全集、格式和空值规则。差异路径可定位到具体变体、记录、字段或 Excel 行/列。JSON 与 Excel 各自对独立预期比较；二者一致并不单独表示业务正确。

本轮在独立测试工作树运行：**原冻结预期 26/26 PASS；扩展草案比较 26/26 PASS，0 项差异。** 比较结果保存在忽略提交的 `03 tests/T3/result/frozen_field_draft/comparison.json`。另将一例的 JSON 销售方和 Excel 销售方分别故意改错，比较器分别报出 `json_invoice_records[0].fields.seller` 和 `excel.rows[0].seller`，证明能分别定位两份产物的字段差异。

本运行只能证明在固定 EML 与事先写好的 PDF 文件级结果下，程序后续主链与该待审核草案相符。它不证明真实 PDF/AI 识别、T3 XML/OFD/图片全链、邮箱真实性、页面和下载包，也不替代用户逐条审核扩展预期。用户确认草案后方可将其改为正式机器标准答案；原冻结预期无需改写。
