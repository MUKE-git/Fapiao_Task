# T2-1 测试设计（按业务场景 B 编号，待审核）

> 上位依据：[业务测试方案](../../DOCS/T2-1_业务测试方案.md)。本文件是第二阶段 Test Design：确定输入组合、执行层次、预期路径和业务结果。尚未制作全部输入文件、编写自动化脚本或执行测试。旧 M01 草稿已删除。

## 约定与判定边界

- **PDF 返回数据**：组件测试使用 `DocumentResult` 的受控返回值，只检验 `pipeline.py` 的调度、组装和交接。真实 PDF 提取能力另做集成测试；不得用受控返回冒充识别通过。
- **邮件输入**：离线用例使用合成 MIME 邮件及模拟 UID；IMAP 行为在 `run_pipeline` 的组件测试中用受控 IMAP 服务响应，真实服务器端到端测试单独报告。
- **业务状态**：T2-4/T2-6 端口缺席时，当前主循环可能把所有记录标为人工待核。用例先检查该发票记录、字段和来源是否正确，再检查待核原因；不能仅凭最终状态判断缺字段规则通过。
- **文件序号**：以下单邮件中的首个保留文件记为 `01`，次个记为 `02`。实际执行时同时检查邮件 UID 与 `file_seq` 的关联。测试用的票号、金额均为虚构值。
- **对比产物**：每例至少留业务结果对比；需要验证路径的用例另留调用顺序和接口输入输出。Excel 比对八列业务值，不用绝对输出路径作判据。
- **状态标签**：下列均为“设计待审核”，不是通过结论；若实现未提供相应能力，执行时记未执行或失败，并说明原因，不改预期迁就代码。

## B00：无未读邮件

### B00-01 空未读集合

- **输入/前置**：IMAP 登录与 INBOX 选择成功；`UID SEARCH UNSEEN` 返回空集合；输出目录为新目录。
- **动作与路径**：调用 `run_pipeline`；完成登录、INBOX 选择、未读搜索及收件箱状态查询后结束，不执行邮件头/正文拉取、附件登记、PDF 处理或 Excel 行写入。
- **预期**：`stats.unseen_total=0`、`invoice_keyword_mails=0`；无发票记录，无新增 Excel 业务行。若系统生成空 `task_debug.json`，内容应为空邮件数组。无 IMAP 错误。
- **证据**：IMAP 指令记录、调用计数、stats、输出目录清单。

## B01：单张 PDF 基础流程

### B01-01 一封相关未读邮件、一张发票

- **输入/前置**：UID `1001`，主题“电子发票 B01”，Date `2026-09-29 09:30 +08:00`，一张 PDF `办公用品发票.pdf`。处理器返回 `DocumentResult(file_seq="01", role="Invoice")`，字段为票号 `12345678901234567890`、日期 `2026-09-28`、金额 `126.40`、发票类型“电子发票（普通发票）”、票面类型“办公用品”、销售方“测试销售方有限公司”。
- **动作与路径**：`run_pipeline` 筛选主题 → `collect_mail_files` 登记 `01` → `process_message` 将 PDF 交 `process_pdf` → `_invoice_record` 组装 → `_excel_rows`/`append_to_summary_excel` → `mail_to_dict`/`_write_debug`。
- **预期**：一封邮件、一文件、一条 b 类 record、一条 Excel 业务行；`record_id=Msg1-01`，`source.source_file_seq=["01"]`；Excel 只有八个业务列，出行时间和出发地/目的地为空。PDF 处理器恰好收到该 PDF 一次。`complete` 不是 T2-1 单独通过条件，待核原因另核。
- **证据**：接口调用记录、`task_debug.json`、工作簿八列与行数、stats。

## B02：一封邮件含多张 PDF 发票

### B02-01 两张发票各成一笔

- **输入/前置**：同一邮件含 `甲发票.pdf`、`乙发票.pdf`。甲返回票号 `11111111111111111111`、金额 `53.93`、销售方“甲公司”；乙返回票号 `22222222222222222222`、金额 `126.40`、销售方“乙公司”。
- **动作与路径**：附件分别登记为 `01/02`；对两个文件各调用一次 `process_pdf`，分别接收 `DocumentResult`。
- **预期**：两条 record、两条 Excel 行；甲只引用 `01` 和甲字段，乙只引用 `02` 和乙字段；没有邮件级合并行。行顺序按输入顺序核对，字段关系按 `file_seq` 核对。
- **证据**：两次 PDF 接口输入输出、JSON `files/records`、Excel 两行。

### B02-02 第二张发票字段不完整，不借第一张字段

- **输入/前置**：沿用 B02-01，乙的处理器结果把发票号码设为 `Not Found`，甲仍完整。
- **动作与路径**：两份文件照常分别处理。
- **预期**：仍有两条发票记录；乙票号维持缺失，绝不复制甲票号；乙进入待核的最终校验归 T2-6，本例先核“记录不丢、字段不串”。
- **证据**：乙的 `DocumentResult` 与乙 record 对照。

## B03：PDF 发票与行程单同封

### B03-01 单发票、单行程单

- **输入/前置**：一张交通类 PDF 发票 `客运发票.pdf`（票号 `33333333333333333333`、金额 `53.93`、票面类型“客运服务”），一张 `行程单.pdf`（金额 `53.93`、出行时间 `2026-09-25 10:00`、路线“杭州→上海”）。两个文件均返回各自的文件级角色。
- **动作与路径**：分别登记、分别经 PDF 处理；发票结果形成 record，行程单结果进入后续匹配入口。
- **预期**：Excel 仅一条发票行，无行程单独立行。按《T2-1_主干交接.md》的业务口径，单对单应直接成组并汇入出行信息、记录行程单来源 `02`。当前主循环在匹配端口缺席时只标待核；若执行结果如此，应报告文档/实现差异，不把它判成“已成组通过”。
- **证据**：两个 PDF 接口结果、行程单匹配入口调用、record 的 `matched_itinerary`、Excel 行。

## B04：非交通类 PDF 发票

### B04-01 b 类没有旅行字段

- **输入/前置**：仅一张票面类型“办公用品”的 PDF 发票；处理器结果中即使误带 `travel_time`、`origin_dest`，也没有行程单文件。
- **动作与路径**：主循环组装 b 类 record 与 Excel 行。
- **预期**：`kind=b类`；JSON record 的 `fields` 不物化旅行字段；Excel 两个旅行字段为空；不因为没有行程单产生缺行程单提示。正式字段校验归 T2-6。
- **证据**：原始 `DocumentResult`、JSON、Excel 与提示列表。

## B14：单张交通类 PDF 发票、无行程单

### B14-01 票面类型“客运服务”

- **输入/前置**：仅一张 PDF 发票；处理器返回票面类型“客运服务”，其他发票字段完整；无行程单。
- **动作与路径**：主循环组装记录并进入行程单匹配入口或端口缺席分支。
- **预期**：`kind=a类`，记录和 Excel 行保留；出行时间、路线为空；有需核对行程单的提示，不能标称已匹配。
- **证据**：kind、status/提示、Excel 旅行字段、匹配入口调用。

### B14-02 票面类型“客运服务费”

- **输入/前置**：仅将 B14-01 的票面类型改为“客运服务费”。
- **动作与路径**：同 B14-01。
- **预期**：同样判为 a 类并提示待核；验证“费”字有无不影响交通类判定。
- **证据**：两例的 kind 与提示对比。

## B05：关键字段缺失

### B05-01 缺发票号码

- **输入/前置**：一张角色明确为 Invoice 的 PDF；处理器返回日期、金额等字段，但票号为 `Not Found`。
- **动作与路径**：主循环接收文件级结果并组装 record。
- **预期**：记录仍存在，来源正确，不从其他文件补票号；正式缺字段校验和“因缺票号待核”的状态判定属于 T2-6。本例不能仅因后续端口缺席造成的通用待核状态就认定缺票号校验通过。
- **证据**：处理器结果、record、待核原因原文。

### B05-02 缺金额或日期

- **输入/前置**：分别让一张 Invoice PDF 缺金额、另一张缺日期；两者使用不同 `file_seq`。
- **动作与路径**：逐文件处理并组装。
- **预期**：两条记录均保留，各自缺失值留在对应记录；不得跨文件补齐。正式格式/必填判定由 T2-6 验证。
- **证据**：逐文件结果与两条 record 对照。

## B06：PDF 角色不明或处理失败

### B06-01 角色 Unknown

- **输入/前置**：一个 PDF 已登记为 `01`，处理器返回 `role="Unknown"`，没有可信发票字段。
- **动作与路径**：主循环接收结果。
- **预期**：`files` 保留该 PDF，`records` 不新增发票；待核提示包含邮件及文件定位线索；Excel 无新增业务行。
- **证据**：`files/records`、提示、Excel 行数。

### B06-02 处理错误但角色仍为 Invoice

- **输入/前置**：处理器返回 `role="Invoice"`、`error_reason="AI_PARSE_ERROR"`，仅有部分发票字段。
- **动作与路径**：主循环接收并组装。
- **预期**：记录保留且待核，错误进入邮件错误信息/提示；不得把部分字段补成其他发票的字段。
- **证据**：错误返回、record 状态与提示、`error_reason`。

## B07：其他文件形态分别分流

### B07-01 仅 XML，处理脚本缺席

- **输入/前置**：邮件只有 `数据.xml`；`StagePorts.document_handlers` 中无 `XML` 函数。
- **动作与路径**：附件登记为 XML；主循环查询 XML 处理入口。
- **预期**：文件可定位，提示 XML 本阶段尚未提取；不生成发票 record 或 Excel 行。
- **证据**：文件类型、接口查询/未调用、提示、记录数。

### B07-02 仅 OFD，处理脚本缺席

- **输入/前置**：邮件只有 `票据.ofd`；无 `OFD` 处理函数。
- **动作与路径**：登记为 OFD，查询 OFD 入口。
- **预期**：提示 OFD 尚未提取；无虚假发票 record/Excel 行。
- **证据**：同 B07-01，核对 `file_type=OFD`。

### B07-03 仅图片，处理脚本缺席

- **输入/前置**：邮件只有 `照片.png`；无 `图片` 处理函数。
- **动作与路径**：登记为图片，查询图片入口。
- **预期**：提示图片尚未提取；无虚假发票 record/Excel 行。
- **证据**：同 B07-01，核对 `file_type=图片`。

### B07-04 仅其他格式

- **输入/前置**：邮件只有 `附件.txt`，属于当前 `_FILE_TYPES` 以外的格式。
- **动作与路径**：登记为“其他”；无对应处理函数。
- **预期**：提示人工核查；不生成发票 record/Excel 行，不静默丢弃附件。
- **证据**：文件登记、提示、记录数。

### B07-05 三种格式各触发自己的已存在接口

- **输入/前置**：同封邮件含 `数据.xml`、`票据.ofd`、`照片.png`；向现有 `StagePorts.document_handlers` 分别注入 `XML`、`OFD`、`图片` 的受控函数，各函数只记录收到的文件并返回 `Unknown`，避免把后续提取能力算入本例。
- **动作与路径**：调用 `process_message`，记录三个函数的输入。
- **预期**：XML 函数仅收到 XML，OFD 函数仅收到 OFD，图片函数仅收到图片；三者均收到正确 `file_seq`/路径；每个函数各调用一次，互不串用。本例只证明**触发接口**，不证明真实 XML/OFD/图片提取、跨格式匹配或 Excel 入表。
- **证据**：三份函数调用清单与文件登记表。

## B08：PDF 与 XML 混合邮件

### B08-01 PDF 发票正常交接、XML 待核

- **输入/前置**：同封邮件含 `发票.pdf`、`数据.xml`；PDF 返回完整发票字段；XML 真实处理脚本缺席。
- **动作与路径**：两个文件均登记；PDF 交给 `process_pdf`，XML 查找 XML 入口后进入待核分支。
- **预期**：一条 PDF 来源的发票 record、一条 Excel 业务行；XML 在 `files` 中且有待核提示；不得声称 XML 字段被提取或 PDF+XML 已匹配。
- **证据**：PDF 接口调用、XML 分支、JSON、Excel。

## B09：无附件

### B09-01 主题相关但无附件

- **输入/前置**：UID `1009`，主题“电子发票通知”，邮件只有正文，无附件。
- **动作与路径**：通过主题筛选，进入单邮件处理，但附件登记为空。
- **预期**：邮件可在调试记录定位；无文件、无发票 record、无新增 Excel 行；出现“无有效附件”提示。
- **证据**：邮件条目、提示、Excel 行数。

## B10：同邮件重复附件

### B10-01 直接附件与 ZIP 内文件内容相同

- **输入/前置**：邮件先附 `甲发票.pdf`，再附 `附件.zip`；ZIP 内 `重复发票.pdf` 字节与甲完全相同，另有字节不同的 `乙发票.pdf`。
- **动作与路径**：`collect_mail_files` 处理直接附件和 ZIP 内两个文件。
- **预期**：甲和乙各保留一次，分别为 `01/02`；重复发票不占第三个序号，不被重复交给 PDF 处理器；`dedup_skipped` 记重复文件名及原因。在两个保留 PDF 均被处理器判为 Invoice 的前提下，最终恰好两条发票记录和两行 Excel，不能用“至多两条”掩盖漏处理乙发票。
- **证据**：附件哈希仅作为测试输入核对，不进业务 JSON；`files`、`dedup_skipped`、PDF 调用次数、record 数。

## B11：ZIP 异常与限制

### B11-01 损坏 ZIP

- **输入/前置**：邮件含正常 PDF 直接附件及一个内容并非 ZIP 的 `坏包.zip`。
- **动作与路径**：正常 PDF 和 ZIP 分别进入附件处理。
- **预期**：ZIP 错误留可定位线索；坏包不生成发票；正常 PDF 的处理不被坏包结果替代。
- **证据**：错误原因、正常 PDF 的文件与记录、提示。

### B11-02 路径逃逸或加密条目

- **输入/前置**：ZIP 内含 `../逃逸.pdf` 或加密条目，并含一份普通 PDF。
- **动作与路径**：解包时检查条目。
- **预期**：违规条目不落到目标目录外，也不成为发票；普通 PDF 可继续登记；违规原因留痕。
- **证据**：目标目录内外文件清单、`error_reason`、`files`。

### B11-03 超出嵌套深度

- **输入/前置**：三层嵌套 ZIP，最内层有 PDF；另有允许深度内的 PDF。
- **动作与路径**：递归解包。
- **预期**：第三层内 PDF 不进入处理链，错误标记深度超限；允许深度内文件仍按规则处理。
- **证据**：文件清单、错误原因、PDF 调用记录。

### B11-04 数量和总大小边界

- **输入/前置**：分别构造 ZIP 解出恰好 50/51 个文件、总量恰好 15MB/超过 15MB 的邮件；每个子例使用独立输出目录。
- **动作与路径**：执行附件收集；不调用真实 AI。
- **预期**：边界内文件可登记；超过任一限制时出现明确错误，超限文件不得当作成功提取。保留超限前已登记文件时，核对其序号和来源；不以总体异常掩盖已成功处理的文件。
- **证据**：生成参数、文件计数、字节数、`error_reason`、已登记文件表。

## B12：有未读邮件但主题无关

### B12-01 所有未读邮件均无关

- **输入/前置**：`SEARCH UNSEEN` 返回 UID `101`、`102`；主题分别“会议通知”“项目周报”，邮件可带附件但主题均不含发票报销关键词。
- **动作与路径**：`run_pipeline` 只读取主题/日期头并筛选。
- **预期**：`unseen_total=2`、`skipped_no_invoice_keyword=2`、`invoice_keyword_mails=0`；不拉取两封邮件完整正文，不调用附件或 PDF 处理，不新增业务行。
- **证据**：IMAP 请求清单、stats、调用计数、输出行数。

### B12-02 相关与无关未读邮件混合

- **输入/前置**：UID `101` 主题“会议通知”；UID `102` 主题“电子发票”，后者含一张发票 PDF。
- **动作与路径**：逐封先筛主题，只处理 UID `102` 的完整邮件与附件。
- **预期**：`unseen_total=2`、跳过数 `1`、相关数 `1`；仅 UID `102` 形成邮件条目及一条发票记录，不把 UID `101` 的附件带入结果。
- **证据**：IMAP 请求、JSON 的 `mail_uid`、Excel 行数。

## B13：拉取中断及输出失败

### B13-01 三封相关邮件，第二封断线后恢复

- **输入/前置**：本轮 `UID SEARCH UNSEEN` 按顺序返回 `201 202 203`。三封邮件主题均为“电子发票”，各含一张内容不同且处理器均判为 Invoice 的 PDF，票号分别为 `20120120120120120120`、`20220220220220220220`、`20320320320320320320`。UID `201` 正常处理；UID `202` 的首次**完整邮件** `BODY.PEEK[]` 拉取抛 `imaplib.IMAP4.abort` 或连接错误，重连后再次按 UID `202` 拉取成功；UID `203` 正常处理。第二封的邮件头拉取成功，故断点确定在正文/附件拉取，不混入主题筛选故障。
- **动作与路径**：运行 `run_pipeline`；记录三封邮件头/完整邮件请求、第二封重试前后的连接、PDF 处理调用及最终输出。重连后沿原 UID 继续，不重新按邮件序号遍历已完成的第一封。
- **预期**：三封邮件均处理一次，UID 顺序与 `mail_id` 的对应关系为 `201→Msg1`、`202→Msg2`、`203→Msg3`；每封各一条发票 record，分别为 `Msg1-01`、`Msg2-01`、`Msg3-01`，共三条 Excel 行。UID `201` 不因重连而重复处理，UID `202` 虽被重试拉取但只形成一条记录，UID `203` 不被漏掉；三条票号各归属其原邮件。`stats.unseen_total=3`、`invoice_keyword_mails=3`、`skipped_no_invoice_keyword=0`，且 `imap_error` 为空。
- **证据**：IMAP 连接及 UID 请求时间序列（特别是 `202` 的失败和重试）、三次 PDF 处理的 UID/文件对应清单、stats、JSON 中三封邮件与三条 record、Excel 三行票号。仅有 Excel 三行不足以证明第一封未重复、第三封未漏掉，必须核对 UID 与记录关系。

### B13-02 Excel 被占用

- **输入/前置**：一张 PDF 发票已形成记录；Excel 写入器返回 `EXCEL_PERMISSION_DENIED`。
- **动作与路径**：主循环调用 `append_to_summary_excel` 并接收错误。
- **预期**：不得记录“Excel 写入成功”；错误进入调试信息/日志，已形成的邮件与发票关系保留以便追查。
- **证据**：写入器返回值、日志、`task_debug.json`、目标工作簿变化情况。

### B13-03 三封相关邮件，第二封连续拉取失败

- **输入/前置**：沿用 B13-01 的三封邮件及 UID 顺序；UID `201` 正常完成，UID `202` 的完整邮件拉取在允许的全部尝试中均失败，UID `203` 尚未开始。
- **动作与路径**：运行 `run_pipeline`，记录第二封的全部重试和最终错误。
- **预期**：`stats.unseen_total=3`、`invoice_keyword_mails=2`、`skipped_no_invoice_keyword=0`，且 `imap_error` 明确报告失败；调试 JSON 保留已完成的 UID `201` 及其一条 record，不出现 UID `202/203` 的虚假完成记录。本轮在写 Excel 之前中断，因此不得声称 Excel 已写入第一封发票；测试报告须依据 UID 请求记录说明 UID `203` 尚未处理，不能将它算作主题跳过。此例检验失败语义，不与 B13-01 的恢复成功混为一个判定。
- **证据**：第二封逐次失败的 UID 请求记录、stats、调试 JSON、Excel 是否有新增行、日志中的失败信息。
