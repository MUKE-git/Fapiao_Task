已确定的 T2-4 范围：

1. 只比较本轮候选发票记录，不读取历史 Excel/数据库；同邮件 MD5 重复附件已由附件处理器处理，不属于本任务。
2. 空票号不比较。非空的相同票号放在一起比较，即使两者同为 `ABC123` 等格式错误的值也照样比较；格式错误由 T2-6 报告。这里的“放在一起”只指查找本轮哪些记录有同一个票号，不会改写原记录。
3. 同票号仅比较五个发票必填字段：开票日期、发票号码、报销金额、票面类型、销售方。发票类型、行程单关联、旅行字段、状态和来源不参与“是否重复”判断。五项一致时，后出现的重复记录直接跳过 Excel；JSON 保留全部原始记录及来源。报销金额按十进制数值比较，不因 `100.0` 与 `100.00` 的显示精度不同而制造冲突。
4. 五项存在冲突时，本阶段实际执行 AI 二次仲裁；XML 优先分支待 T3 接入。AI 不能明确选出已有候选时，每个不同的冲突候选仍各入 Excel 一行，状态均为“人工待核”；完全重复的后续记录仍跳过 Excel。AI 不得创造第三套字段值替换原记录。
5. 所有候选经本阶段处理后仍须继续通过 T2-6 校验和三关键字段全缺的入表筛选；不以仲裁结果代替校验，也不覆盖上游已有待核状态。

## 3. 现有代码接线与实现难点

- `stage_ports.py` 已预留 `dedup_arbitrator.py::arbitrate_records(mails: list[MailRecord]) -> list[MailRecord]`。这正是 T2-4 应开发的模块，负责本轮发票号码重复检查、字段冲突 AI 仲裁和结果提示；T2-3 只负责行程单匹配。它在匹配后、校验前调用；开工前缺席时会使发票标为人工待核，本阶段已补上该模块。
- 当前 `pipeline._excel_rows(mails)` 与 `_write_debug(cfg, mails)` 共用仲裁返回的 `mails`。若直接从 `mail.records` 删除相同记录，会丢失用户要求保存在 JSON 的原始记录和来源；需要以最小接线改动把 Excel 写入选择与完整记录快照分开，同时保持已有公开入口签名。
- `InvoiceFields.invoice_number` 就是发票号码。相同号码且五项一致时，后续记录直接跳过 Excel；若五项冲突则先仲裁，不能仅凭号码把一方悄悄删掉。程序需要一个仅供写 Excel 使用的跳过清单，因为 JSON 仍须保存所有原始记录；这不是新增发票业务字段，也不新增“重复”状态。`dedup_skipped` 专门记录按 MD5 跳过的重复附件，不拿它记录发票。
- 现有 AI 接口负责首次逐文件提取。本阶段新增一次联合仲裁调用：把同票号冲突组的全部候选、邮件主题/时间、附件清单、相关 PDF 的文字、来源文件原名、五个必填字段和具体差异一起提交；输出只允许选择一个已有 `record_id`，附逐项原文证据，或返回无法确认。提示词及返回校验由本阶段模块维护；模型给出第三种字段值、无证据、证据不能在原文中找到或请求失败时，全部冲突候选人工待核。这里的仲裁不声称证明发票真伪。
- 相同票号的仲裁过程用可定位提示记录哪些 `record_id` 跳过 Excel、哪个被 AI 选中或为何待核。原始 JSON 记录、状态枚举和八列 Excel 结构不另加“重复”取值。

## 7. 用户批注的具体落点

1. `dedup_arbitrator.py` 是 T2-4 模块，本阶段开发。
2. “重复直接跳过”具体指：扫描到同票号、五项必填字段一致的后续发票时，不把它再写为 Excel 新行；`task_debug.json` 的原始发票与来源不删除。例如第一封和第二封邮件各有号码 `ABC123`、五项相同的发票，Excel 只有第一张对应的一行，JSON 两封邮件各保留自己的发票记录。`ABC123` 仍是格式错误，由 T2-6 后续报错。
3. 用户确认仅五个发票必填字段参与一致性比较。若同号但金额一个 100、一个 200，这是冲突，不按先后直接跳过；调用 AI 对照各来源。AI 无法选出时，两种不同候选都写 Excel 并标人工待核。
4. 原 `excel去重.txt` 的“有效票号”容易被理解为格式正确的 20 位号码；用户已明确要求相同的非空错误号码也比较，因此本阶段将该图的判定文字改为“非空票号”。这不表示错误号码被当成正确号码；T2-6 仍负责报告格式错误。
