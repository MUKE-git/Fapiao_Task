## 2. 本阶段验收边界

验证同一邮件内以 a 类发票为主记录的一对一关联；金额精度、相等层和 0.5 容差；完整解码原名尾缀；多票竞争时唯一明确尾缀优先；确认后逐轮重算和末尾单对单；异常来源、b 类及未知类别的数量边界；匹配关系、原金额、旅行字段、全部行程单和待核原因在 JSON/Excel 中的交接。验证接入真实匹配端口，并核对后续仲裁、校验阶段缺席时的提示归属。

真实 IMAP、AI 服务准确率、实际附件命名分布、T2-4 去重仲裁、T2-5 专项来源规则和 T2-6 完整字段校验分别记录为未覆盖或其他任务，不借 T2-3 的通过结果宣称这些能力已验收。可脱敏的真实文件名与人工对应关系可供后续评估名称规则的实际适用性，但不作为离线匹配算法测试的前提。

## 3. 执行顺序与每步产物

1. **基线与契约核对**：记录当前 Git 状态、被测文件和用例哈希；按最新规则逐项列出可观察结果；审阅 `itinerary_matcher.py`、端口、主流程和现有测试入口，记录规则或文档冲突，不静默修改冻结材料。
2. **复跑已确认用例**：使用现有固定用例入口的受控提取模式，重点审查 C05、C13～C19，并保留 C01～C22 必选范围回归。逐例保存命令、输入版本、实际 JSON/Excel、匹配关系、提示和差异。C18 提示短语先复核业务含义及具体输出，区分文案差异与算法差异；不自动改预期。
3. **补齐逐字段机器核对**：依据用户已确认的预期与独立业务规则，给 JSON、Excel 的约定业务字段建立逐行标准答案、列映射、类型/格式与空值规则。标准答案不得由程序实际输出反向生成。复用现有测试入口输出具体到用例、文件、行、字段的差异；受控提取和真实本地 PDF 模式分别标识。
4. **设计 T2-3 新用例草案**：覆盖现有用例缺少的 2026-10-09 修订行为：唯一明确尾缀解决多票争一单、逐轮重算、末尾单对单金额不同或缺失、剩余多项仍不唯一、无/多张明确尾缀的冲突、b 类/未知类别/异常来源不制造单对单，以及候选顺序变化和重复调用。每条草案先提交输入、独立制定的逐字段预期、规则依据和反例供用户审核；审核通过才编号入库和执行正式比较。
5. **独立专项测试与集成复测**：对已审核的新旧用例验证匹配器、实际端口、JSON/Excel 交接；对边界缺陷做最小复现。必要时把真实本地 PDF 模式作为识别链对照，注明 AI 被模拟失败及上游字段差异，不混入受控匹配验收计数。
6. **缺陷、修复复测与阶段结论**：每项差异附输入、规则、预期、实际、复现命令及影响范围，区分产品缺陷、测试脚本问题、预期/文档冲突和上游识别问题。研发修复后以同输入复测并跑相关回归；最终报告列通过数、遗留问题、未测范围和是否达到 T2-3 独立验收条件。

## 4. 关键检查点

| 层级 | 独立核对内容 |
| --- | --- |
| 算法 | 相等层优先；原值差值 ≤0.5；0.50 包含、0.51 不作为金额候选；无金额候选时明确尾缀可兜底；无唯一证据不按顺序或最近金额猜测。 |
| 逐轮关系 | 同邮件初始及末尾一票一单；一单最多一票；唯一明确尾缀优先只裁决已有拟关联；确认后重算；冲突项仍计入剩余数量。 |
| 数据来源 | 匹配只使用同邮件完整解码原名和已持久化行程单字段；发票号码、销售方、内部文件名不作为关联证据；来源断链或重复序号不生成关系。 |
| 输出 | 仅 a 类建立关系并汇入所选行程单的时间、起终点；保留发票金额、行程单原始精度和全部未匹配行程单；用户 Excel 一发票一行，行程单不另起行。 |
| 稳定性 | 记录/附件顺序变化及相同输入重复调用不改变已确定关系、不累积相同待核原因；中间歧义最终解决后不误报。 |

## 5. 判定口径

正式通过须同时满足：已审核用例的受控提取结果符合逐行逐字段标准答案；T2-3 新增用例均经用户审核后执行并通过；关联、提示和来源无未解决的 T2-3 关键缺陷；缺陷复测及相关回归有可重放证据。若输出与确认的预期不同，先记录差异并定位，不因研发自测通过、JSON 与 Excel 彼此一致或模拟输入通过就宣称业务正确。
