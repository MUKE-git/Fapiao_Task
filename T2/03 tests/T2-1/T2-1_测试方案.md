# T2-1 主循环测试方案（待审核）

> 依据：《重构方案.md》《计划分工.md》《项目结构与任务边界.md》《PRD.md》《字段表.txt》。本文件定义测试方法和预期，不记录实际执行结论。

## 1. 测试目标与边界

验证 `run_pipeline(cfg, log) -> (mismatches, stats)` 所承担的主循环职责：收取并筛选邮件、调度附件与 PDF 处理、将每张 PDF 发票组织成独立记录、产生待核提示，以及将业务行交给 Excel 写入器、将邮件记录序列化为 `task_debug.json`。

T2-1 的流程完整性以**环节调用及数据交接**为判据，不能只看最终 Excel 是否有行。这里的“可观察”指测试在模块接口放记录器，保存调用顺序、输入标识和返回标识；记录器仅用来观察/提供预设返回值，不增加业务步骤。PDF 预读和单文件处理的实际能力属于 T2-1 旧版 PDF 能力适配范围，但若相应脚本未交付或未接通，只能用受控替身验主循环调用契约，不能宣称真实 PDF 链通过。T2-3 是行程单多对多匹配，不是 PDF 预读任务。

XML/OFD/图片在 T2-1 中只登记并提示待核。XML 字段提取、PDF+XML 跨格式匹配及其结果入表属于 T3；不纳入本次通过标准。T2-3 多对多行程单匹配、T2-4 写表前去重仲裁、T2-5 完整来源双向定位、T2-6 差异化字段校验也分别验收；本阶段仅核查 T2-1 已承担的接口和基础关系。

## 2. 测试材料与审核顺序

每个用例执行前固定以下材料，交项目方审核后才运行：

1. **输入邮件**：可重复生成的 `.eml`，列出主题、Date、UID、附件原名、物理类型、内容标识及附件顺序。需要 ZIP 时同时保存 ZIP 原件和内部清单。测试邮箱不是必需材料。
2. **处理器返回值**：`processor_returns.json`，按文件序号给定附件登记、PDF 预读与 PDF 提取的返回值或指定异常。不同发票使用不同票号和金额，以检查字段串用。
3. **预期路径**：`expected_trace.json`，逐文件列出必须调用、不得调用的环节及数据传递顺序。调用记录应至少包含 `mail_uid`、`file_seq`、处理环节、输入文件标识、输出记录标识；不把仅有最终产物当作路径证据。
4. **预期产物**：`expected.json` 和 `expected_excel.csv`，写定每封邮件的 `files`、`records`、`dedup_skipped`、`error_reason`、待核提示、统计值，以及 Excel 八列和预期行数。

执行后另存 `actual_trace.json`、实际 `task_debug.json`、实际 `.xlsx` 和 `diff.md`。比较器逐项报告“预期/实际/是否通过”；预期文件不能在看过实际结果后静默修改。若测试替身的接入需要调整，保留修订记录并重新审核预期。

### 路径记录示例

一封邮件含两张 PDF 发票时，预期路径是：

```text
邮件 UID 1001 → 附件登记(01, 02)
01 → PDF 预读 → PDF 单文件处理 → record Msg1-01
02 → PDF 预读 → PDF 单文件处理 → record Msg1-02
两条 record → Excel 行组装 → Excel 写入器
邮件及两条 record → 数据模型序列化 → task_debug.json
```

每次调用的输入、输出在 `actual_trace.json` 中留证。如果某环节没有可观察的调用点，不能用最终结果推断它被调用；该项标记“未验证”，并报告缺少调用证据的原因。

## 3. 测试层次与判定方法

| 层次 | 原材料 | 验证方式 | 可以证明的范围 |
|---|---|---|---|
| 主循环契约测试 | 合成 `.eml` + 受控附件/PDF 返回值 | 调用记录与预期路径逐环节比较；JSON/Excel 与人工预期比较 | 调度、隔离、组装、输出、异常传播 |
| 附件链联调 | 合成 `.eml` + 真实小文件/ZIP，PDF 提取可受控 | 检查文件登记、去重、存盘及传递给 PDF 环节的文件 | 真实附件处理与主循环衔接 |
| PDF 链联调（条件项） | 独立取得且可公开用于测试的 PDF 样例 | 先确认实际 PDF 处理脚本及主循环接线已交付，再对预读、提取、主循环、输出逐环节留证 | 只有接线完成后才能执行并证明真实 PDF 链；现阶段不得预记通过 |
| 邮箱联调 | 专用测试邮箱 | UID 搜索、`BODY.PEEK`、重连及未读状态前后对照 | 真实 IMAP 兼容性；无邮箱时明确列为未验证 |

主循环契约测试和附件链联调证明主干行为。PDF 链联调依赖 PDF 处理脚本与主循环实际接通；未交付时标“未执行”，并在 T2-1 验收结论中明确这一缺口。真实邮箱联调依赖测试环境。任何一层都不能用替身结果冒充真实处理结果。

## 4. 用例清单与预期

| 编号 | 输入与处理器设定 | 必经路径及关键预期 |
|---|---|---|
| M01 | 一封主题相关邮件、一张 PDF 发票；预读为 Invoice，提取六个业务字段 | 收件→附件登记→PDF 预读→单文件处理→一条 record→Excel 一行→JSON 一封；来源指向该 PDF |
| M02 | 一封邮件含两张 PDF 发票；返回不同票号、金额、票面类型 | 两张 PDF 分别预读与处理，各生成一条 record、Excel 两行；不得复制另一张发票的字段 |
| M03 | 一张 a 类 PDF 发票和一张行程单 PDF | 两文件分别处理；仅发票成行；按 T2-1 已锁定的一对一直接成组，行程字段从行程单汇入并记录其文件序号 |
| M04 | 一张 b 类 PDF 发票，无行程单 | 发票一条 record、Excel 一行；旅行字段为空，不因无行程单提示缺凭证 |
| M05 | PDF 提取结果缺发票号码或日期 | 仍保留一条发票 record，`status=人工待核` 并给出待核提示；核查 Excel 行与状态的当前新版契约，不因缺字段丢掉 record |
| M06 | PDF 处理返回错误或类型 Unknown | 错误及待核信息可定位到邮件/文件；不能借用同邮件其他 PDF 的字段，也不能伪造完整发票 |
| M07 | 一封邮件仅含 XML、OFD、图片 | 三文件登记并逐类提示待核；不调用 PDF 提取，不生成发票 record，不产生 Excel 发票行 |
| M08 | 一封邮件含 PDF 发票和 XML | 两文件登记；PDF 走预读及单文件处理并形成发票行；XML 走待核分支；不调用 XML 提取、跨格式匹配，不以 XML 字段改写该行 |
| M09 | 无附件或仅不支持文件 | 按实际文件形态登记/提示；无发票 record；不得静默结束 |
| M10 | 直接 PDF 与 ZIP 内相同内容，另有不同内容 PDF | 同邮件重复内容只保留首份；`dedup_skipped` 有原因；保留文件序号连续，未重复处理相同 PDF |
| M11 | ZIP 两层及超深、超数量、超总大小、损坏包、危险路径 | 合规文件进入登记/处理；不合规项留错误或待核证据，不造成路径逃逸或虚假发票行 |
| M12 | 未读集合混有无关主题邮件 | 先按主题筛选；无关邮件不拉取完整内容、不处理附件；统计值与实际一致 |
| M13 | IMAP 拉取中断、重连，`logout()` 异常 | 可恢复时按 UID 继续，避免重复或错配；退出异常不改变已处理结果的成败语义 |
| M14 | 同一封邮件同时含 PDF、ZIP、XML 等多种文件 | 文件形态分别分流；每个保留文件的登记记录与其路径一致；最终文件数、记录数、提示数可逐项解释 |

M10～M11 的限制值按文档为 ZIP 递归最多两层、解出文件最多 50 个、总大小最多 15 MB。大文件边界测试可用受控文件流或临界大小测试材料，保留生成方式，避免把不可复现的大二进制文件作为唯一证据。

## 5. 通用检查项

- `task_debug.json` 每封邮件一个条目；每张被识别的 PDF 发票对应一条 record；行程单不独立成行；无发票候选时不创建虚假记录。
- `record_id`、`source.source_file_seq`、`files.file_seq` 可在同一邮件中对应；一对一行程单汇入时 `matched_itinerary.file_seq` 指向真实登记的行程单。
- 用户 Excel 表头与顺序严格为：发票日期、发票号码、报销金额、发票类型、票面类型、出行时间、销售方、出发地/目的地；不含 UID、文件序号、状态等内部列。
- 输出行的字段只能来自对应 PDF 处理结果或已成组的行程单；不能从同邮件另一张发票取值。
- 只检索未读且主题相关邮件，读取邮件使用不主动置已读的方式；对真实邮箱是否保持未读，须在邮箱联调中验证。
- `stats`、待核提示、`error_reason` 与实际经过的分支一致；缺字段发票按新版方案保留记录并标人工待核。

## 6. 通过标准与报告格式

核心用例 M01～M09、M12、M14 的预期路径及产物全部满足，且无发票串字段、虚假记录、静默丢附件、错误写入业务列等缺陷，才可判 T2-1 主干通过。M10～M11、M13 中属于 T2-1 调用链的部分必须有结果；若依赖尚未交付的附件实现或真实邮箱，则明确标“未执行/未验证”，不得记为通过。

最终报告逐用例列：审核版本、输入材料、预期路径、实际路径、预期产物、实际产物、差异、证据文件和结论。总体结论区分“主循环契约通过”“附件/PDF 联调通过”“真实邮箱联调通过”三个层级，不以其中一个替代另一个。
