# T2-1 业务测试方案（定稿）

> 本文件只确定业务场景、验收目标和测试层次。具体邮件数据、处理器预设值、断言脚本和实际结果属于后续“测试设计”“自动化实现”。依据《重构方案.md》《计划分工.md》《项目结构与任务边界.md》《PRD.md》《字段表.txt》，并以当前根目录实际代码核对测试落点。若代码继续变化，执行前须复核下述映射。

## 一、业务范围与验收口径

T2-1 验证新主循环能按邮件和附件分流，把 PDF 交给单文件处理接口、接收处理结果，形成“一张 PDF 发票一笔记录”，输出业务 Excel 和可追溯的 `task_debug.json`；暂未支持的 XML/OFD/图片文件须登记并提示待核。**PDF 预读如何识别类型、票号或金额，不是 `pipeline.py` 主循环的功能验收项**；主循环只须正确调用处理器并使用其返回的数据。

**阶段边界**：T2-3 才验多对多行程单匹配；T2-4 验写表前发票号码去重仲裁；T2-5 验完整来源双向定位；T2-6 验正式差异化字段校验。XML/OFD/图片提取、PDF+XML 跨格式匹配及下载链接获取属 T3。T2-1 可验“文件类型 → 对应处理接口”的触发与数据交接：向已存在的 `StagePorts.document_handlers` 注入受控处理函数，检查 XML/OFD/图片分别进入自己的处理函数；若真实处理脚本尚未接入，则同时验默认待核分支。**接口触发测试不等于真实处理脚本及后续匹配、入表全链路通过**。

**字段与结果状态的职责**：`pipeline.py` 负责把文件级结果组装成发票记录及 Excel 业务行，保证行数、来源、字段归属和八列输出正确；`excel_writer.py` 负责实际创建或追加工作簿。字段是否缺失及其正式校验规则属于 T2-6，主循环负责接收校验结论、保留记录并传递待核提示。按新版方案，关键字段缺失的发票不得丢弃。当前 `pipeline.py` 在 T2-4、T2-6 端口缺席时还会将本轮记录标为“人工待核”；因此 T2-1 验收不以 `complete` 作为单张正常 PDF 的必要条件，也不能用这一状态证明缺字段校验已完成。

**触发路径的判据**：本阶段利用现有的 `StagePorts.document_handlers` 等接口边界，在测试中接入记录调用的受控函数，验证主循环是否按文件类型调用对应处理函数及传递正确文件标识；不要求研发增加只供测试使用的业务函数。真实 XML/OFD/图片提取、跨格式匹配和入表全链路，要在相应脚本交付后另做集成测试。后续研发须保持明确、稳定的接口及来源标识，供各阶段交接与核验。

## 三、业务场景（Given–When–Then）

### B00 无未读邮件

**Given** 本轮收件箱没有未读邮件。  
**When** 用户运行处理。  
**Then** 系统报告未读数为零；不进入附件处理，不生成发票记录或新增 Excel 业务行；用户能区分“没有未读邮件”与“处理失败”。

### B01 未读且主题相关的单张 PDF 发票

**Given** 收件箱中有一封未读、主题含发票关键词的邮件，含一张可被 PDF 处理器识别为发票的 PDF；该发票可以是交通类或非交通类。  
**When** 用户运行本轮处理。  
**Then** 系统登记该附件、将其交给 PDF 处理器，并依据处理器返回的发票结果建立一条记录，在业务 Excel 产生一行；JSON 中该记录能指向本邮件及该附件。这里验主循环传递与组装，不以测试 PDF 预读准确度代替。交通类/非交通类的附加要求分别见 B14/B04；若后续仲裁/校验尚未接入，记录可以因该缺口标待核，不能因此丢失发票记录。

### B02 一封邮件含多张 PDF 发票

**Given** 一封相关未读邮件含两张内容不同的 PDF 发票，且两张票的票号、金额和销售方不同。  
**When** 系统处理该邮件。  
**Then** 每张发票各形成一条记录和一行 Excel；每条记录只采用对应 PDF 的字段和文件来源，不合并成邮件级单行，也不跨票复制字段。

### B03 PDF 发票与行程单同封

**Given** 一封邮件含交通类 PDF 发票及 PDF 行程单。  
**When** 系统分别处理两个文件。  
**Then** 发票成为记录，行程单不单独成为 Excel 行。按《T2-1_主干交接.md》所述，单发票、单行程单应直接成组并将行程字段汇入发票；多对多的正式配对才属于 T2-3。当前代码将匹配交给可选的 `StagePorts.match_itineraries`，缺席时只标待核；这与交接文档的单对单口径存在差异，验收时应作为待确认项报告，不能悄悄放宽预期。

### B04 非交通类 PDF 发票

**Given** 邮件仅含一张票面类型不属于交通关键词的 PDF 发票。  
**When** 系统组装发票记录及业务行。  
**Then** 该发票归为 b 类，行程单不单独成为必要输入；Excel 的出行时间和出发地/目的地为空，JSON 不凭空物化旅行字段。正式 b 类字段校验归 T2-6。

### B14 单张交通类 PDF 发票、无行程单

**Given** 相关未读邮件只有一张票面类型命中交通关键词的 PDF 发票，没有行程单。  
**When** 系统组装发票记录。  
**Then** 该发票归为 a 类，保留记录和 Excel 行，并提示“缺行程单/需人工核对”，不得凭空填入出行时间或出发地/目的地。交通类判定应采用关键词子串匹配，覆盖“客运服务”和“客运服务费”。

### B05 关键字段缺失

**Given** PDF 已判定为发票，但处理结果缺少发票号码、日期或金额之一。  
**When** 系统组装本轮结果。  
**Then** 发票记录仍保留，并向用户提供可定位的人工待核提示；不得把缺失字段从同邮件另一附件补来。关键字段规则及最终校验由 T2-6 验收。

### B06 PDF 角色不明或处理失败

**Given** 邮件含 PDF，但处理结果角色为 Unknown，或处理器返回错误。  
**When** 主循环接收该文件级结果。  
**Then** 文件仍可在邮件登记中查到；错误或类型不明进入待核信息。角色不明时不得伪造发票行；处理失败但仍明确判为发票时，保留发票记录并标待核。

### B07 尚未支持的文件形态：分别验证 XML、OFD、图片和其他

**Given** 相关未读邮件分别只含 XML、只含 OFD、只含图片或只含其他格式文件。  
**When** 系统处理每一种邮件。  
**Then** 四种文件分别按自己的物理类型登记。XML/OFD/图片若对应处理脚本尚未接入，各自提示本阶段未提取/需人工核对；“其他”始终走其他格式待核分支。默认情况下均不虚构业务字段、发票记录或 Excel 行。

**触发路径的单独判据**：在组件测试中，给现有 `StagePorts.document_handlers` 分别配置 `XML`、`OFD`、`图片` 的受控处理函数；对应文件只触发对应函数，不触发别的类型函数。当前代码可通过此接口测试分流，不必等待 T3 脚本完成；真实 `xml_processor.process_xml`、`ofd_processor.process_ofd`、`image_processor.process_image` 的提取结果及后续链路，须等脚本交付后再验。

### B08 PDF 与 XML 混合邮件

**Given** 相关未读邮件同时含一张 PDF 发票和一个 XML 文件。  
**When** 系统处理两个附件。  
**Then** 主循环把 PDF 交给 PDF 处理器，并依据返回结果形成记录；XML 登记并待核；不得宣称已从 XML 提取字段或已完成 PDF+XML 匹配。后者是 T3 的独立流程完整性测试。

### B09 无可处理附件

**Given** 相关未读邮件没有附件。  
**When** 系统处理该邮件。  
**Then** 不产生发票记录及 Excel 行，并给出“无有效附件”类提示，可凭邮件主题和时间定位。

### B10 同邮件重复附件

**Given** 同一封邮件的直接附件与 ZIP 内文件内容相同，另有一个不同内容的有效附件。  
**When** 系统收集附件。  
**Then** 相同内容只进入处理链一次，重复项记入 `dedup_skipped`，其余附件继续处理；不会因重复内容产生额外发票行。本轮跨邮件同票号仲裁不属于本场景。

### B11 ZIP 异常或限制超出

**Given** 相关邮件附有损坏、加密、危险路径或超出文档层数/数量/大小限制的 ZIP。  
**When** 系统尝试解包。  
**Then** 不安全或不合规条目不得进入正常发票处理；邮件留下可定位的错误或待核线索，合规的独立附件不应被误写为该异常文件的结果。

### B12 有未读邮件，但全部与发票报销无关

**Given** 收件箱有未读邮件，但所有邮件主题均不含发票或报销关键词。  
**When** 用户运行处理。  
**Then** 系统报告未读数大于零、主题相关邮件数为零、主题跳过数等于未读数；不拉取这些邮件的完整附件内容，不产生发票记录或新增 Excel 业务行。此场景专门区分“有未读但不相关”和 B00“无未读”。本方案不测试邮件已读状态变化。

**测试意义与优先级**：B00 只能验证空输入，不能证明主题筛选有效；B12 验证有未读邮件时无关邮件不会进入附件处理或报销表，属于高优先级的基础功能场景，不是性能测试。

### B13 收件中断及输出失败

**Given** 拉取某封邮件时连接中断，或输出 Excel 时文件被占用。  
**When** 系统按既有重试或错误处理路径运行。  
**Then** 不把失败伪装成处理成功；已形成的记录和错误线索尽可能保留在调试输出；Excel 写入失败有明确错误提示。具体重试次数可在测试设计中按代码和文档逐项核对。

## 四、需求追踪矩阵（RTM）

本矩阵把第一节的业务范围、第三节的场景与第二节的真实代码责任关联起来。一个场景可能覆盖多项特性；一项特性也可能需要多个场景。下列“代码责任”只标识测试落点，不表示该实现已经通过。

| 业务特性/要求 | 性质 | 场景 | 主要代码责任 | 业务结果判据 |
|---|---|---|---|---|
| 无未读与无关未读的区分 | 功能、用户提示 | B00、B12 | `pipeline.py::run_pipeline`；`stats.unseen_total`、`stats.skipped_no_invoice_keyword`、`stats.invoice_keyword_mails` | B00 未读数为零；B12 未读数大于零但相关数为零；两者均不进入附件链 |
| 仅处理目标未读邮件 | 功能、筛选 | B01、B12 | `pipeline.py::run_pipeline` | 主题相关的未读邮件进入处理；无关邮件只看主题后跳过 |
| 每张发票独立成笔 | 功能、数据隔离 | B01、B02 | `pipeline.py::process_message`、`_invoice_record`；`DocumentResult` | 发票数与记录数一致，字段与来源不串票 |
| PDF 文件级结果正确交接 | 接口、数据完整性 | B01、B02、B06、B08 | `pipeline.py::process_message` → `pdf_processor.py::process_pdf` → `DocumentResult` | 每个 PDF 分别交接；主循环使用对应处理结果；不以此判定预读识别准确度 |
| 行程单不单独入表及单对单关系 | 功能、业务归属 | B03 | `pipeline.py::process_message`、`_apply_matching`、`_excel_rows` | 行程单不成 Excel 行；单对单汇入的阶段口径按文档与代码差异单独确认 |
| b 类不虚构旅行字段 | 数据正确性 | B04 | `pipeline.py::_invoice_record`、`_excel_rows`；`data_model.py::mail_to_dict` | b 类业务行旅行字段为空，JSON 不写无来源的旅行字段 |
| 交通类无行程单需待核 | 功能、异常处理 | B14 | `pipeline.py::_invoice_record`、`_apply_matching`；`TRANSPORT_RECEIPT_KEYWORDS` | a 类记录仍输出；没有行程单时明确待核，不虚构旅行字段 |
| 缺失/不确定结果进入人工核查 | 异常处理、可追溯性 | B05、B06 | `pipeline.py::process_message`、`_invoice_record`；`InvoiceRecord.status` | 已认定的发票记录保留，待核原因能定位，未知角色不伪造发票 |
| 按物理格式分流 | 功能、阶段隔离 | B07、B08、B09 | `attachment_processor.py::collect_mail_files`；`pipeline.py::process_message`；`StagePorts.document_handlers` | PDF 交给 PDF 处理器；XML/OFD/图片各自触发对应处理函数或缺席提示；其他走待核；无附件有提示 |
| 同邮件内容去重和 ZIP 安全限制 | 功能、容量边界 | B10、B11 | `attachment_processor.py::collect_mail_files`；`DedupSkipped` | 重复内容不重复处理；违规内容不形成业务行，异常可定位 |
| 输出业务表和来源记录 | 数据完整性、可追溯性 | B01、B02、B03、B04、B08、B10 | `pipeline.py::_check_source_chain`、`_excel_rows`；`excel_writer.py::append_to_summary_excel`；`data_model.py::mail_to_dict` | Excel 仅八业务列；JSON 中记录能指向邮件与文件 |
| 中断或输出失败不伪装成功 | 容错 | B13 | `pipeline.py::run_pipeline`、`_write_debug`；`excel_writer.py::append_to_summary_excel` | 错误明确报告，已知失败不显示成成功 |

这里的“容量边界”指文档给定的文件数量、ZIP 大小和深度限制；本方案尚未定义处理时延、吞吐量等性能指标，不能据此宣称覆盖性能测试。用例编号、执行结果和缺陷号待第二、第三层工作时补入追踪表。

## 五、测试层次及各自回答的问题

### 文档与代码的待确认差异

- **单对单行程单**：《T2-1_主干交接.md》称 T2-1 已支持直接成组；当前 `pipeline.py::_apply_matching` 在匹配端口缺席时一律标待核。B03 按文档提出业务预期，执行前应确认以哪个版本的阶段边界为准。
- **关键字段缺失**：新版业务口径要求保留记录并标人工待核；正式缺字段校验属于 T2-6。当前 `_invoice_record` 只在 `DocumentResult.error_reason` 存在时直接设待核，后续端口缺席又会使所有记录待核。T2-1 检查记录保留、字段不串用和状态/提示交接；不可因最终状态相同就认为 T2-6 校验已通过。

| 层次 | 必要性与适用场景 | 真实落点 | 证明范围 |
|---|---|---|---|
| 单元测试 | 用于需要精确判定的纯组装规则：B02、B04、B05 的记录/业务行，来源链关系 | `_invoice_record`、`_excel_rows`、`_check_source_chain`、`mail_to_dict` | 字段映射、行数、来源及输出结构；不证明邮件或 PDF 真正被处理 |
| 组件测试 | 用合成邮件和可控 PDF 文件级结果覆盖 B01～B09；用真实 ZIP 内容覆盖 B10～B11 | `process_message`、`collect_mail_files`、`process_pdf` 的模块边界 | 单邮件分流、附件登记及主循环与文件级结果交接；替身场景不证明实际识别能力 |
| 集成测试 | 把附件、PDF 处理、主循环、数据模型和 Excel 写入器连起来，覆盖 B01/B02/B08 的真实数据流 | `run_pipeline` 及上述实际模块 | 环节接线和产物一致性；只有 PDF 处理能力交付并接通后才可认定真实 PDF 链通过，其识别准确度仍需处理器自身测试 |
| 端到端测试 | 用隔离的测试邮箱和用户入口覆盖 B00/B12/B13，检查收件到可见输出 | `app_demo.py` → `run_pipeline` → IMAP/输出目录 | 真实 IMAP 筛选、界面与落盘行为；无测试邮箱时标未执行，不以模拟 IMAP 代替 |

测试设计阶段应为每个场景选择最低足够层次，再为跨模块风险加必要联调。不同层次的通过结论分别报告，不合并为一句“系统已通过”。用户保留的真实邮件作为后续盲测材料，本方案不要求提前取得。

### 业务验收结论的写法

每个场景报告“通过 / 未通过 / 未执行 / 不属于 T2-1”，并写明所依据的测试层次。T2-1 的核心阻断缺陷包括：漏处理相关邮件、发票合并或串字段、无来源或来源错位、未支持形态虚构发票、关键字段缺失时丢记录、Excel 泄露内部列、异常静默吞掉。

若 PDF 实际链、真实邮箱或后续阶段端口未就绪，结论必须写清缺口，不能用替身测试或预留接口代替真实联调通过。
