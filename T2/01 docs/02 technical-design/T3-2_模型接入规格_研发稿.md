# T3-2 模型接入规格（研发稿）

日期：2026-10-15。归属《计划分工》T3-2，由研发设计与实现；产品只审核最终页面提示和交付行为。本稿是开工契约，不表示程序已实现或模型调用已测试。规划上按 T2 已完成且通过测试衔接，实际联调时核对代码状态。

## 1. 任务边界

- 一个文件一次提取调用，输入带 `file_seq`、原文件名、文件真实格式、预读角色与该文件可读内容；输出仅对应该文件。不得把一封邮件的多个文件拼成一次提取结果，也不得让模型决定发票与行程单或跨格式凭证的配对。
- PDF/OFD 可提取文本时走文本适配；图片和必须看版面才能判断的文件走多模态适配。XML 的结构化字段由 T3-3 确定性解析，模型不能覆盖有效 XML 值。OFD 有结构/文本则优先本地读取，必要时转换后走 PDF 文本或页面图像分支。
- 模型接入只返回**文件级候选值与证据**。T3-3～T3-5 的处理器做格式专属解析和本地规则校验；T3-6 做同票合并；T2 仲裁/字段校验及主流程决定最终记录和 Excel。二次仲裁只用于《重构方案》§4.3 指定的无 XML 同号冲突，不替代上述确定性环节。

## 2. 统一输入与输出

建议在现有 `DocumentResult` 之前设一个内部模型适配层；具体函数名由研发确定，不改 `stage_ports.py` 公开处理器调用形状。文本与多模态适配层均接收同一身份信息，返回同一业务结果形状。

| 项 | 约束 |
|---|---|
| 输入身份 | `mail_id`、`file_seq`、`original_name`、内部存盘名、真实格式；文件标识不可由模型生成。 |
| 输入内容 | 单文件的文本片段或页面图像；保留页码/区域等证据位置。限制输入大小和页数，超限显式返回待核原因，不静默截断关键页。 |
| 分类 | `Invoice` / `Itinerary` / `Unknown`；`file_classifications` 长度必须为 1，`file` 必须等于本次输入的内部文件名（含真实扩展名）。 |
| 发票字段 | 号码、开票日期、价税合计、发票类型、票面类型、销售方；日期和金额使用现有数据模型规则。 |
| 行程单字段 | 匹配金额、首笔出行时间、首段起终点；编号由程序分配，不由模型填写。 |
| 缺失与证据 | 缺值明确标缺失；每个非空候选关联来源文件及可见文本/页码，无法提供证据的值降级待核。模型不得填充输入中不存在的值。 |

适配层先解析返回 JSON，再做本地结构校验：对象形状、字段类型、分类枚举、单文件数量、文件名对应、日期/金额格式；金额以十进制解析，不经 `float`。格式错误与字段缺失分开记录。模型返回 `Unknown` 表示无法判断，不等于与另一个明确分类“判断不一致”；P10 只在明确判断相反时触发。模型输出是候选，不能证明发票真伪、文件完整或签章有效。

## 3. 模型与供应商适配

1. 保留当前百炼接入作为第一实现；配置分别指定文本和视觉模型，不把现有 `dashscope_model` 同时当作两类模型的兼容保证。适配层隐藏供应商 SDK 的请求、响应和错误对象，业务处理器只接收统一结果。
2. 文本调用可沿用当前 `Generation.call` 路径；视觉调用使用支持图像输入的多模态接口。研发在实现时按已安装 SDK 版本及所选模型能力核对参数。优先使用模型支持的结构化输出选项；无论服务端是否承诺 JSON，仍执行本地结构校验。官方 API 说明：[DashScope API 参考](https://help.aliyun.com/zh/model-studio/qwen-api-via-dashscope)、[结构化输出说明](https://help.aliyun.com/zh/model-studio/qwen-structured-output)。
3. 密钥只从运行配置/密钥环境取得，不写入提示词、日志、JSON、ZIP 或页面；请求应按调用传入密钥，避免并发任务共用可变全局密钥。提示词可先保留内置，但把“逐文件提取”和“二次仲裁”分开版本管理，记录版本号而不在用户输出中写入完整敏感输入。
4. 默认串行调用以保持来源和错误定位；若实际延迟要求并行，再启用有上限的并发队列及限流，不跨文件共享模型输出。失败文件不阻断同邮件其他文件。

## 4. 失败、重试与回退

| 失败类型 | 研发处理与记录 |
|---|---|
| 429、5xx、暂时网络超时 | 最多重试 2 次，间隔可沿用现有 1 秒、3 秒并加少量抖动；超过上限后记录服务错误并进入本地可用提取/待核。 |
| 认证错误、非法请求、不支持模型/输入 | 不盲目重试；记录可排障的错误码，不把密钥或原始响应泄露给用户。 |
| HTTP 成功但 JSON 不可解析、分类长度/文件名错误 | 视为无效模型结果；保留原响应的脱敏诊断摘要，本地兜底仅填有明确证据的字段，余项待核。不能把兜底结果伪称“AI 已识别”。 |
| 部分字段缺失或格式错误 | 保留同文件已确认字段，缺失与无效字段分别标记；不把行程单字段从发票或其他文件补入。 |

沿用 P22 的用户提示边界：模型服务失败时页面说明自动识别未完成，并展示本地已得到和仍需核对的字段。内部错误码用于调试，不直接作为生硬的用户文案。

## 5. 二次仲裁

仅在本轮同票号记录冲突、无 XML 来源且确定性规则不能裁定时，由 T2 去重仲裁环节发起一次**冲突组级**模型判断。输入包含候选记录 ID、同组邮件定位、各候选的来源文件与可见证据、逐字段差异；不得输入无关邮件或完整带签名下载 URL。输出只允许“选中一个已有候选 ID + 证据理由”或“无法确定”。模型给出第三组新业务值、选中不存在的 ID、理由与证据不符、接口失败时，一律人工待核；不得静默覆盖或丢弃冲突来源。XML 来源存在时按已确认的 XML 优先规则走，不调用二次仲裁替代。

## 6. 当前代码差距与交接检查

当前 `ai_client.py::call_ai_audit_and_rename` 原自旧版，可把多份 PDF 文本拼成一次请求，并伴随临时副本重命名；`pdf_processor.py` 已通过副本把它包成单文件调用。T3-2 应将“调用模型”“校验单文件结果”“用户导出命名”分开，避免模型模块改写源文件或决定交付名。当前 `pipeline.py` 设置全局 `dashscope.api_key`，并无视觉适配；这些是实施差距，不是已完成能力。

研发交接至少提供：文本与视觉各一份固定输入/规范输出样例；无效 JSON、分类不对应、429/5xx、超时、部分字段缺失的实际结果；一组无 XML 冲突的二次仲裁“选中/未决”样例；运行日志脱敏检查。测试侧再分别标记受控响应测试与真实服务联调，不能互相代替。接口细节和模型选择由研发负责，产品只审核 P10/P22 等最终页面行为。
