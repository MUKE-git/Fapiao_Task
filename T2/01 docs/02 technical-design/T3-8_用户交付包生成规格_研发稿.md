# T3-8 用户交付包生成规格（研发稿）

日期：2026-10-21。归属《计划分工》T3-8，专责**后端交付物生成**：选择一份已确认的票据 PDF、业务命名、原名与交付名映射、Excel/JSON 定稿后组装并核查 ZIP。页面呈现、文案和下载控件属于 T3-1；跨格式业务匹配属于 T3-6；统一主流程调用顺序与临时运行目录属于 T3-9。本稿沿用已确认的交付边界：“申请单”指“行程单”，用户票据只含发票及行程单 PDF。

## 1. 用户收到什么

- **用户 Excel**：`发票信息汇总表.xlsx`，仅八列，按现有规则逐笔追加**本轮**记录；每轮新建工作目录和汇总表，不向历史运行的表格追加。行程单不另占一行。JSON 金额保留十进制原精度，Excel 显示两位。
- **调试文件**：`task_debug.json`，保留邮件、文件、发票记录、全部行程单和来源信息，供追溯与核查。
- **用户票据**：只放实际可交付的发票 PDF 与行程单 PDF。XML、OFD、图片可以是识别输入或 PDF 转换来源，但原格式不交付；未知角色文件不放入用户票据。
- **内部处理文件**：继续用 `Msg{邮件序号}_{文件序号}_{安全名}` 登记和处理。内部目录与用户交付目录隔离；`1_Downloaded_Zips/`、`2_Extracted_PDFs/`、原始邮件 ZIP、过程文件及日志均不进入用户 ZIP。
- **交付产物**：从 T3-9 提供的本轮独立工作目录读取确认过的来源，交付目录与工作文件隔离；只生成供 T3-1 页面下载的精简 ZIP，不把临时工作目录整体打包。工作目录创建与生命周期由 T3-9 负责。

## 2. 票据 PDF 的选择与业务文件名

同一张发票可能同时有 XML、PDF、OFD 等来源，先按 T3-6 规则形成同一业务记录，再选择交付凭证；不得把每种来源格式各导出一份。行程单按其自身记录选择 PDF。两份 PDF 即使字节不同，只要票号等关键业务信息一致且均通过凭证检查，就属于同票的重复来源，交付一份即可：优先原始 PDF；同优先级时按文件登记顺序选首份，其余来源仍留在 JSON。**同号但金额、日期等关键字段冲突**属于另一种情况：先按 XML 优先及本轮仲裁规则确认业务记录；仍无法确认时，不随意选 PDF 交付，保留冲突来源和前端待核提示。

| 场景 | 用户票据中的结果 |
|---|---|
| 已有可用的原始 PDF | 交付该 PDF 的业务名副本；PDF 优先于同票 OFD/图片转换件。 |
| 无原始 PDF，但有可用 OFD | 取 T3-4 已转换且检查通过的 PDF 交付；不交付 OFD。 |
| 无原始 PDF/OFD，但有可用票据图片 | 取 T3-5 已转换且检查通过的 PDF 交付；不交付图片。 |
| 只有 XML 发票 | 保留结构化发票记录并标“缺凭证”，不凭空生成票面 PDF；`用户票据/` 无该发票文件。 |
| 转换失败、角色无法确认或业务值冲突且凭证无法唯一选择 | 不交付未经确认的 PDF；JSON 记录原因，页面给出对应待核提示。其他已确认票据继续交付。 |

优先级只在**已成功生成且通过检查**的候选 PDF 中比较：OFD 转换失败而同票图片可用时，可继续用图片形成交付 PDF。原始 PDF、转换后的 PDF 均应确认文件可读取且内容与选定来源对应；改扩展名不能代替转换。OFD/图片转 PDF 只改变交付形态，不改变原来源格式、提取结果和匹配证据。链接下载得到的 PDF 按同一规则处理。

| 交付角色 | 文件名模板 | 取值来源 |
|---|---|---|
| 发票 PDF | `{票面类型}+{业务日期}+{金额}元.pdf` | 类型和金额取该发票记录的 `receipt_type`、`total_amount`。有 `matched_itinerary.file_seq` 时，通过同邮件行程单记录取首笔 `travel_time` 的日期；未匹配时取该发票 `invoice_date`。不得按文件顺序或金额猜行程单。 |
| 行程单 PDF | `行程单+{出行日期}+{金额}元.pdf` | 日期取选中行程单自身的首笔出行日期。若其 `record_id` 被同邮件唯一发票记录的 `matched_itinerary.file_seq` 指向，金额取该发票 `fields.total_amount`；未匹配时取该行程单自身 `match_amount`。不得按附件顺序猜测关联。 |

已匹配发票金额缺失或无效时，文件名使用 `金额缺失`，不得退回采用行程单票面金额。已匹配行程时间缺失或无效时，两份文件名使用 `日期缺失`，不得退回采用开票日期；关联指向不存在的行程单时交付失败，不猜测日期。若多笔发票记录指向同一行程单，交付金额来源不唯一，应停止该行程单的自动业务命名并报告交付失败，不任选一笔。跨邮件即使出现相同的行程单票面金额，也只按**各自邮件内的已确认关联**命名。例：两封邮件分别有 21.10 元、34.20 元发票，各自附有出行时间为 2031-05-06、票面金额 55.30 元的行程单，两个发票及行程单导出名均用 `2031-05-06`，分别以 `21.10元`、`34.20元` 结尾；JSON 中两条行程单的 `match_amount` 仍各为 55.30。文件名是交付归属标签，不声称 PDF 票面金额或发票开票日期被改写。

### 日期、金额、票面类型的文字处理

1. 日期在有值且有效时统一用 `YYYY-MM-DD`。行程单取首笔行程日期；已匹配发票取其所关联行程单的首笔行程日期，未匹配发票才取自身开票日期。
2. 金额用十进制文本，保留上述选定金额来源的有效输入小数位（最多四位），不先用二进制 `float` 或固定两位四舍五入。**Excel 显示两位不改变 JSON 或文件名所取金额的原精度**。金额文本不带 `¥`、逗号或空格。
3. 票面类型按既有 `*一级*二级` 规则取二级并清理存盘禁用字符。不能从另一文件的票面类型补这个文件的导出名。
4. 缺日期用 `日期缺失`，缺金额用 `金额缺失`，缺票面类型用 `票面类型缺失`。**金额缺失后不加“元”**：例如 `票面类型缺失+日期缺失+金额缺失.pdf`；有金额时才是 `...+121.74元.pdf`。占位仅用于文件名，不改 JSON 的业务值。字段有值但格式错误时也不得把错误文本写入文件名，应使用相应占位并提示具体错误。

### 文件名安全和 JSON 映射

- 导出扩展名一律 `.pdf`。清理路径分隔符、控制字符和 Windows 非法文件名字符；不得写出 `用户票据/`。完整解码原名仍保留在 JSON。
- 同名交付 PDF 按文件登记顺序加 `(1)`、`(2)` 避免覆盖，按大小写不敏感比较。扩展名和重名后缀都计入完整名称最多 120 字符。
- 超长时只截断业务名主体并加短摘要，保留扩展名和重名后缀；摘要由该文件稳定信息计算，确保同一文件重复计算得到同名。先预留后缀长度，再裁剪，最终完整文件名不超过 120 字符。
- `files[].exported_name` 仅在该来源被选中并实际交付 PDF 时填写对应业务文件名。未选中的 XML/OFD/图片、重复来源、未知文件和仅 XML 的来源保持空值；不能把同一交付 PDF 冒记为每个来源各交付一次。若从 OFD/图片转换，选中的原来源文件条目填写所生成的 PDF 名称，`original_name`、`internal_name` 保持原义。
- `internal_name` 是处理时的内部存盘名，**不表示该文件存在于交付 ZIP 中**。JSON 保留原邮件定位、原文件名、文件序号和导出名，不能让用户误以为内部路径可在 ZIP 内打开。

## 3. 下载 ZIP 内容

```text
fapiao_时间戳.zip
└─ Invoice_Task/
   ├─ 发票信息汇总表.xlsx
   ├─ task_debug.json
   └─ 用户票据/
      ├─ 客运服务费+2026-04-27+121.74元.pdf
      └─ 行程单+2026-04-27+121.74元.pdf
```

示例只表示包内结构和命名，不表示给定 A 组样本存在行程单。若本轮没有可交付 PDF，可不创建 `用户票据/`；Excel 与 JSON 仍按主流程生成，并显示相应缺凭证/待核提示。不把整个临时工作目录直接打包。

生成顺序：T3-9 先得到各处理器已完成并检查的 PDF 候选；T3-8 再选择应交付的 PDF、业务命名、填写相应 `files[].exported_name`，由 T3-9 序列化最终 `task_debug.json`，T3-8 最后构建 ZIP。ZIP 完成后逐项核对 Excel、JSON、每份应交付 PDF 和包内清单；同时确认包内未出现 XML、OFD、图片、原始 ZIP、内部目录或日志。不以“ZIP 字节非空”代替完整性检查。

## 4. 交付结果状态与失败边界

| 场景 | T3-8 返回给 T3-1 的结果 |
|---|---|
| 处理成功 | 返回已生成且通过内容检查的 ZIP 及成功状态；T3-1 决定按钮显示。 |
| 汇总表未生成 | 不进入 ZIP 制作；由 T3-9 返回汇总表失败状态，供 T3-1 显示 P25。 |
| 汇总表已生成，随后打包或完整性检查失败 | 返回交付包失败状态，不返回可下载 ZIP；T3-1 显示 P26，不同时显示 P25。 |
| 用户点击按钮后浏览器传输失败 | 不属于交付包制作失败；由 T3-1 处理页面上的再次下载。 |

研发核对现有 `delivery_exporter.py`、`utils.py::zip_directory_to_bytes` 与 `utils.py::format_amount_text` 的实际行为：交付 ZIP 不得混入内部目录或静默跳过读不到的文件，导出金额不得经 `float` 丢失原精度。该模块即使已在 T2 并行工作中出现，也须按本规格核对 T3 全格式来源和最终 ZIP；不把既有文件名当作已完成验收证据。T3-8 只返回清晰的产物/失败状态，不直接写页面提示。

## 5. 产品已确认的交付边界与任务交接

用户交付包只保留汇总表、`task_debug.json` 和发票/行程单 PDF；“申请单”指行程单。不再提供本机桌面输出模式，本机运行也只从页面下载 ZIP。缺失占位使用 `日期缺失`、`金额缺失`、`票面类型缺失`，金额缺失后不加“元”。OFD/图片到 PDF 的格式转换分别由 T3-4/T3-5 产出并自检；T3-8 只从可交付的 PDF 候选中选取、复制、命名和打包，并核查最终包。T3-9 保证 Excel/JSON 与交付包之间的生成顺序和同一轮来源关系。
