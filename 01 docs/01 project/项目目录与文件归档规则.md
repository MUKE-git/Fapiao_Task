# 项目目录与文件归档规则

> 本文是本项目目录归属的操作说明，供开发者、测试人员和后续 AI 工程师开工前查阅。它说明新增或移动文件应放在哪里；具体业务规则和模块接口以《重构方案.md》及对应任务交接文档为准。

## 1. 目录总览

| 位置 | 放什么 | 归档判断 |
|---|---|---|
| 项目根目录 | 当前版本运行时 Python 模块及应用入口 | 当前代码采用根目录平铺导入。新版运行模块继续放根目录，除非一次明确的包结构重构同时更新所有导入、启动方式和测试。不要把运行模块放进文档、开发记录或测试资料目录。 |
| `01 docs/01 project/` | 产品需求、项目说明、总体方案、任务计划、项目结构与协作规则 | 描述要做什么、为什么做、模块边界是什么。业务契约以《重构方案.md》为准。 |
| `01 docs/02 technical-design/` | 流程图、实体关系、字段定义、类图、Excel 规则等技术设计 | 描述系统按什么结构和规则实现。与总体方案冲突时，先记录冲突并按评审后的契约修正文档，不自行选一份覆盖另一份。 |
| `02 build/<任务号>/` | 研发侧任务交接、实现记录、开发决策和研发自测代码/记录 | 回答研发实现了什么、开发过程中如何自测、交付边界是什么。研发自测留在此处，即使文件是 Python 测试代码。 |
| `03 tests/<任务号>/` | 测试工程师的测试方案、测试设计、缺陷、独立验收脚本和验收结果 | 回答测试如何验证、发现了什么、验收结论是什么。不要把研发自测材料误归到这里。 |
| `03 tests/<任务号>/scripts/` | 测试工程师维护的可执行测试脚本 | 脚本从本目录运行时，输入、导入路径及结果路径都应指向实际目录，不得继续写入旧目录。 |
| `03 tests/<任务号>/result/` | 对应任务最近或正式的测试报告、机器可读结果和原始测试日志 | 结果要能追溯到测试脚本、命令、用例及日期；运行器写出的结果也必须落在这里。 |
| `04 logs/` | 本地运行产生的调试日志 | 属于运行痕迹，不是设计文档或验收结论；日志通常被 Git 忽略。若某段日志要作为缺陷证据，应在测试记录中说明来源和对应问题。 |
| `99 other/` | 已确认暂不属于当前运行链、但还不适合删除的历史或待归类文件 | 这是暂存区，不是长期随手堆放区。新增时在本目录说明文件来源、用途、为何暂存；确认彻底无用后再清理。 |
| `T1/` | T1-7 旧版快照 | 只读行为基线，不参与新版运行。不要在此开发新版功能。 |
|  |
| `__pycache__/` | Python 自动生成的字节码缓存 | 生成物，不手工整理或提交。 |
| `.streamlit/` | Streamlit 本机配置及示例密钥配置 | 真实密钥留在本地忽略文件中；仓库只保留无真实凭据的示例。 |
| `.git/` | Git 版本控制数据 | 工具维护目录，不放项目资料，不手工改内部文件。 |

## 2. 新增文件时按用途选择位置

先判断文件的主要用途，再放置：

1. **程序运行时会导入的 Python 模块**：放项目根目录，与当前平铺模块结构一致。新增 PDF/XML/OFD 等处理器或业务模块时，先核对《项目结构与任务边界.md》和 `stage_ports.py` 的接口约定。
2. **用户需求、产品行为、总体决策和协作约定**：放 `01 docs/01 project/`。
3. **字段、数据关系、流程图、格式或计算规则**：放 `01 docs/02 technical-design/`。
4. **某项研发任务的说明、交接、开发过程自测**：放 `02 build/<任务号>/`。
5. **测试工程师制定或执行的独立测试**：放 `03 tests/<任务号>/`，脚本进 `scripts/`，结果进 `result/`。
6. **运行日志**：放 `04 logs/`；日志一旦用于报告缺陷，要在相应测试/缺陷文档中引用，不能只留在日志目录。
7. **来源明确但当前无正式归属、又需要暂存的旧文件**：放 `99 other/` 并登记说明。若文件仍被代码、文档、脚本或运行入口引用，它就不属于“其他”。
8. **可再生成的临时产物**：放入对应任务结果目录或专用输出目录，并按需要加入 `.gitignore`；不要散落在根目录。

## 3. 任务资料如何配对

同一个任务号可以同时有研发资料和测试资料，但两边各自维护：

```text
02 build/T2-3/     研发方案、实现说明、研发自测、研发交接
03 tests/T2-3/     测试方案、测试设计、测试工程师脚本、缺陷和验收证据
```

任务号应与《计划分工.md》一致。任务尚未编号或边界未确认时，不要擅自编造正式任务号；先放在已有上级文档中记录待定事项，或询问项目负责人。

## 4. AI 工程师开工和归档检查

每次新增、移动或改名文件前后，按以下顺序检查：

1. 先读本规则、`项目结构与任务边界.md`，再读当前任务对应的方案/交接和接口文档。
2. 搜索现有文件和引用，确认不是已有内容的重复副本，也没有运行时代码、测试运行器或文档链接依赖旧路径。
3. 根据第 2 节确定唯一归属；一个文件只保留一个权威版本，其他文档链接到它，不复制出另一份“最新版”。
4. 移动或改名后，更新 Python 导入、测试运行命令、输出路径、相对文档链接和相关说明。
5. 检查 Git 状态，确认只影响本任务范围；按任务要求运行相应检查，并在交接中记录结果与未验证项。
6. 不因文件名看起来像临时文件、当前没有直接导入或内容陌生就直接删除。先检查历史用途和所有引用；需保留但暂不归类时进入 `99 other/` 并记录理由。

## 5. 文档权威顺序

- 产品行为和需求：`PRD.md`；已冻结的技术/业务契约：`重构方案.md`。
- 任务编号、分工和进度：`计划分工.md`。
- 代码职责、目录边界和新旧版规则：`项目结构与任务边界.md` 与本文。
- 某阶段具体交付、已知限制和验收证据：对应的 `02 build/<任务号>/` 交接文档及 `03 tests/<任务号>/` 测试结果。
- 实际运行行为：当前新版根目录代码；旧版行为对照只读 `T1/`。

发现这些来源相互矛盾时，先记录矛盾并指出涉及的文件，不能静默挑选一份内容覆盖其他内容。
