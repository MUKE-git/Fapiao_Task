# 发票邮件处理系统 PRD

本文定义发票邮件整理的用户问题、产品范围、业务规则和验收条件，供产品、研发、测试共同核对。使用与配置见[README](../../README.md)，数据结构、算法及接口见[重构方案](重构方案.md)。

当前产品验收已全部通过。具体用例的预期审核状态与各次运行结果见第八节，分别保留原始记录。

## 一、产品背景与目标

### 1.1 要解决的问题

整理一批报销材料，需要逐封查找邮件、取得文件、识别票据、核对对应关系、填写汇总表，再给票据命名归档。所需发票、行程单分散在多封邮件、直接附件、压缩包和正文下载链接中，整理过程费时费力费眼。

本项目围绕这条任务链设计，重点处理三类问题：

| 原有任务 | 主要负担或风险 | 产品应提供的帮助 |
|---|---|---|
| 找邮件、取附件、解压文件 | 操作重复，容易漏掉邮件或压缩包中的票据 | 按统一入口批量取得本轮相关文件 |
| 识别、抄录和汇总字段 | 多张票据可能串值；发票金额与行程单金额容易混用 | 逐文件提取，一张发票形成一笔业务记录 |
| 对应行程单、核查异常、整理交付文件 | 关系不唯一或字段缺失时，用户难以定位原件 | 自动处理可确定关系；保留来源、待核原因和可下载结果 |

以上是本项目的需求分析，不作为已完成用户访谈或大规模调研的证明。

### 1.2 产品目标与效果依据

让用户从“逐封下载、逐张录入”转为“批量处理、集中核查、下载结果”，减少重复操作，同时让不确定的结果能够回到原邮件核对。

| 目标 | 可观察的产品结果 | 当前证据边界 |
|---|---|---|
| 减少重复整理 | 一次提交后完成收件、获取文件、字段汇总及结果打包 | 产品验收通过；用户反馈提效良好 |
| 减少人工抄录 | 发票逐笔进入固定八列汇总表，行程信息按确认关系汇入 | 用例及测试分别验证，不能以单个样本推断整体准确率 |
| 保持可核查 | 异常能定位邮件及已有文件信息，JSON 保留记录与来源 | 来源可追溯不等于票据真实或字段必然正确 |

目前没有可核对的人工／自动耗时对照数据，不给出节省百分比、整体准确率或处理时延承诺。后续如量化提效，应对同一批材料记录人工整理时间、自动运行时间及人工复核时间，并独立核对结果质量；该测量尚未完成。

### 1.3 非目标

- 不做发票真伪、签章或税务平台查验，不承担报销审批。
- 不自动标记邮件已读，不管理用户的邮箱状态。
- 不做跨轮历史发票去重，不建立长期票据档案。
- 不长期保存邮件内容；工作文件按每轮临时目录的清理规则处理。

## 二、目标用户与核心场景

**目标用户：** 通过邮件接收电子发票及行程单、需要集中整理个人报销材料的报销人员。

**核心场景：** 准备报销时，用户需要将分散在多封邮件中的票据整理成汇总表，并取得便于提交的 PDF。用户接入邮箱并发起处理，系统批量获取相关未读邮件中的材料、提取字段、匹配行程单并生成结果包；对于缺失、冲突或关系不确定的结果，用户根据提示回到原邮件核对。

**任务完成标志：** 用户取得本轮汇总表及可交付的票据 PDF，能够定位需要人工核对的邮件和文件，并在核对后使用整理结果准备报销材料。

## 三、本阶段范围与关键取舍

本阶段围绕完整任务链组织需求；下表说明交付范围和产品取舍，不重排原开发任务。

| 范围 | 本阶段选择 | 取舍及用户影响 |
|---|---|---|
| 核心闭环 | 邮箱接入 → 文件获取 → 逐文件识别 → 匹配与仲裁 → 校验 → 汇总和 ZIP 下载 | 用户能够一次取得整理结果，无需分模块操作 |
| 异常兜底 | 缺失、格式错误、关系不唯一、服务或交付失败须保留明确原因 | 自动化以可核查为边界，不能靠猜测制造完整结果 |
| 业务单位 | 一发票一笔；行程单补充旅行信息 | 避免把一封邮件的多张发票合成一行，或将行程单重复计入报销金额 |
| 发票与行程单关系 | 当前仅支持一对一；按已确认数量、金额及原名规则匹配 | 多张发票共用一份多笔行程单尚未支持，不以金额合计相等推断归属 |
| 同票多格式 | 确认同票后合并来源；有可靠 XML 票号来源时，发票业务值只取 XML | PDF／图片用于凭证交付，不补 XML 缺失业务字段；补空问题已列后续迭代 |
| 交付方式 | 本机、云端均下载本轮 ZIP | 每轮独立处理，仍可能重复处理同批未读邮件 |
| 格式范围 | PDF、XML、图片及条件触发的正文链接 | 保留当前可交付路径，不承诺 OFD 提取或转换 |

## 四、端到端流程

**用户流程：** 
准备邮箱接入 → 填写信息并发起处理 → 查看处理结果 → 有异常则回原邮件核对 → 下载并使用报销材料

**业务流程：** 
主题筛选 → 附件／正文链接分流 → 同邮件内容去重与文件登记 → 逐文件提取 → 同票跨格式组合 → 行程单匹配 → 本轮票号去重仲裁 → 字段校验与入表筛选 → Excel／JSON → PDF 选择、业务命名和 ZIP → 页面下载及人工核查

完整分支以[主流程图](../02%20technical-design/主流程图mermaid.txt)为准。提取只形成候选；匹配、仲裁和校验完成后才统一输出，处理器不直接写汇总表。

## 五、功能需求与业务规则

保留 US-1～US-10 编号，便于与已有资料对应。

### US-1 邮箱登录与收件

**用户需求：** 输入邮箱信息后，能够进入自己的收件箱处理材料。

- 预设 163、QQ、126、Yeah，其他 IMAP 服务器可手动输入；用户须先启用协议及所需授权码。
- 网易邮箱按兼容要求发送 IMAP ID，QQ 等其他邮箱不发送该指令。
- 登录失败时给出中文原因，区分账号／授权码、地址解析、SSL、超时等问题。

### US-2 未读邮件筛选

**触发与结果：** 登录成功后，只检索 INBOX 未读邮件；仅主题含“发票／报销／报销凭证／电子发票／开票”关键词的邮件进入文件处理。

- 附件名和正文不是邮件相关性筛选依据；无关主题邮件整封跳过。
- 不自动标已读。无未读邮件与有未读但主题均未命中须分别提示，并提供服务器侧总数／未读数，帮助用户对照邮箱。
- 不阅读无关邮件，保护用户隐私。

### US-3 文件获取与登记

**用户需求：** 相关邮件中的文件能统一收集，来源可找回，重复附件不重复处理。

- PDF、XML、图片进入对应处理路径。OFD 在登记前忽略；明确 OFD 链接不请求，通用链接取得 OFD 后也忽略。
  - 有非 OFD 附件时只走附件分支，不检查正文链接；否则检查票据下载链接。普通 ZIP 本身算附件，带文件名的 inline 部件也可能算附件。
- ZIP 递归最多两层、解出文件最多 50 个、总大小最多 15 MiB；不安全或超限内容不得当作成功处理。
- 同一邮件内相同字节的文件按 MD5 去重；不同邮件不按附件 MD5 删除来源。
- JSON 保留完整解码原名；存盘名清洗非法字符，无名或不可用名使用 Attachment 加序号并保留实际扩展名。完整存盘名最多 120 字符，含邮件／文件编号、扩展名及重名后缀；超长主体截断加短摘要，同名不覆盖。
- 单个获取失败须留下已有定位信息和原因，不能用“没有附件”代替下载失败。链接安全及资源限制见[下载规格](../02%20technical-design/T3-7_邮件正文下载链接规格_研发稿.md)。

### US-4 文档角色判定

**业务结果：** 区分发票、行程单与无法判断的文件，不能将物理格式当作业务角色。

- PDF 预读按原名关键词优先形成角色提示，“行程单”优先于“发票”，再与单文件识别结果核对；明确分类相反时提示人工确认。
- 图片优先采用内容识别角色。图片可读取、模型角色未知且未标多张独立票据时，才用文件名形成待核候选；模型角色明确且与文件名相反时使用模型角色并提示冲突。
- 文件名不能证明内容属于发票，也不能提供票号、日期或金额。无法判断时保留文件登记及原因，不伪造发票记录。

### US-5 逐文件提取、同票组合与行程单匹配

**用户需求：** 各张票据的值彼此隔离，只有可确认的关系才自动汇总。

| 对象 | 取值与使用规则 |
|---|---|
| 发票 | 提取开票日期、号码、价税合计、发票类型、票面类型、销售方；报销金额取同张发票的价税合计（小写） |
| 行程单 | 保存程序分配的编号、自身匹配金额、首笔行程起始时间、首段起终点；不提取企业名称，未匹配项也保存 |
| 分类与必填 | 发票类型可空，有值查规则；其余五项发票字段必填。票面类型清理星号及分类简称后检查文字类型、缺失及长度，再按交通关键词判 a／b；缺失或无效时不默认 b 类 |
| 旅行字段 | 仅由匹配的行程单汇入 a 类发票；b 类不汇入、不校验旅行字段。票面类型不做有效值清单及 PDF 票面位置核验 |
| 金额精度 | 内部按 Decimal 十进制计算，不提前舍入两位；有效金额最多四位小数，JSON 用字符串保留原始位数，Excel 显示两位。超精度／非法输入保留供核查，不静默截断 |

- 一次首次提取处理一个文件，分类结果仅对应该输入；关系判断由程序完成。XML 结构化解析与 PDF／图片模型提取分别处理。
- 同票跨格式组合保留全部已确认来源；多 XML 冲突或无法可靠确定关系时保留待核。XML 不由 PDF／图片补空的现状及后续问题见[计划分工](计划分工.md)。
- 同邮件初始或确认配对后恰好剩余一票一单时，按既定规则成组，不要求金额完整或相等；数量按全部剩余记录计算，不能过滤 b 类、未知类或异常来源来制造单对单。
- 其他数量组合先比较金额：按较低精度四舍五入后相等层优先，否则用原始差值 ≤0.5 的容差层；层内不唯一再用完整原名尾缀消歧，无金额候选时允许明确尾缀兜底。
- 多票争一单时，只有一票具有明确对应尾缀则优先确认它；无或多票明确对应时，相关项待核，独立关系继续。每轮确认后重算剩余项，不按最近金额或附件顺序猜配对。
- 发票金额与行程单金额各自保留，不互相代填；金额不同本身不新增异常提示。已存在的缺失、格式错误及待核原因仍保留。

### US-6 提取失败、重试与入表兜底

**业务要求：** 区分服务失败、字段未取得和字段有值但无效，不将兜底结果说成模型识别成功。

- HTTP 429／5xx 最多重试两次，间隔 1 秒、3 秒；失败不自动更换型号。
- 有可读 PDF 文字时，可用本地规则保留能够取得的字段；图片或不可读内容不能凭正则补造。未取得字段保留缺失标记（如 FIELD_NOT_FOUND）和核查原因。
- 票号、日期、金额三项全部缺失的发票不入用户 Excel，JSON 保留记录及原因；只缺一项或两项仍入表并提示。有值但格式错误另行判断，不当作缺失。
- 首次提取的文本／图片模型同属已接入的 DeepSeek 或千问家族，型号可不同；实际权限与输入能力取决于服务端。提示词外置于根目录 `prompts.txt`。配置入口见 README，技术请求与扫描 PDF 输入边界见[模型规格](../02%20technical-design/T3-2_模型接入规格_研发稿.md)及[扫描件说明](../../PDF扫描件修复说明.md)。

### US-7 汇总、去重与来源记录

- 每轮独立生成 `发票信息汇总表.xlsx`，表头固定八列：**发票日期、发票号码、报销金额、发票类型、票面类型、出行时间、销售方、出发地/目的地**。同轮追加行，不向历史表追加。
- 行程单不单独成为 Excel 行；b 类旅行两列留空。入表单位为发票，仍受三关键字段全缺和本轮去重选择约束。
- 本轮同非空票号比较五项必填字段；发票类型、旅行字段、状态和来源不参与判重。XML 来源优先，无法确定时保留人工待核；无 XML 来源的冲突组才进入 AI 仲裁。文字证据可核对时只允许选择已有记录；视觉仲裁当前仍保留人工核对。完整条件见[仲裁规则](../../02%20build/T2-4/T2-4_规则与AI仲裁说明.md)。
- 附件内容去重和发票业务判重分别处理；不查历史 Excel。JSON 保留原始业务记录、全部行程单、来源及未入表原因，不因 Excel 跳过某项而删除其记录。
- `task_debug.json` 关联邮件、文件、业务记录、内部名和导出名；结构见重构方案 §3.3。用户 Excel 仅含业务列，完整追源依赖 JSON。

### US-8 用户压缩包文件命名规则
用户下载包只含 `发票信息汇总表.xlsx`、`task_debug.json` 和 `用户票据/` 下的发票、行程单 PDF。XML、图片用于识别，图片可转成 PDF；OFD 直接忽略，不提取、不转换、不参与匹配或交付。原格式、原始 ZIP、内部处理目录和日志不交付。以下模板只作用于实际交付的 PDF；内部保留 Msg{序号}_{文件序号}_{安全名}，JSON 保存原来源与交付名对应关系。
- 发票:`{票面类型}+{业务日期}+{金额}元.pdf`；已与行程单匹配时，业务日期取所关联行程单的首笔出行日期；未匹配时取发票自身开票日期。
- 行程单:`行程单+{出行日期}+{金额}元.pdf`
- 行程单已与同邮件 a 类发票建立唯一关联时，导出名中的金额取**该关联发票**的价税合计；日期仍取行程单首笔出行日期。未匹配行程单的导出名金额取其自身匹配金额。文件名金额只表示本次交付对应的发票金额口径，不改行程单 PDF 票面或 JSON 中的 `itineraries[].match_amount`、`matched_itinerary.match_amount`；两者允许不同。
- 已匹配的发票和行程单属于同一组，两个交付文件名使用同一笔行程的出行日期；发票 JSON 中的 `fields.invoice_date` 仍保存实际开票日期，`fields.travel_time` 及行程单 `travel_time` 仍保存出行时间。关联行程时间缺失或无效时命名用 `日期缺失`，不许悄悄改用开票日期。
- 同一业务凭证有多种格式时优先交付已有 PDF；无 PDF 时，图片经转换并检查后可交付 PDF。仅有 XML 而无票面凭证时保留记录并提示“缺凭证”，不生成虚构票面。未知角色文件不交付。具体选择及异常规则见《T3-8_用户交付包生成规格_研发稿.md》。
- 同名文件自动加 (1)(2) 避免覆盖。缺日期、金额、票面类型分别用 `日期缺失`、`金额缺失`、`票面类型缺失`；**金额缺失后不加“元”**。除同组已匹配票据互用行程日期与发票金额这两项明确规则外，文件名不借其他文件字段；关联发票金额缺失时使用金额缺失占位，不回退借行程单金额。完整导出名最多 120 字符，含后缀；超长加短摘要。


### US-9 人工核查提示

**用户需求：** 知道哪些结果需要核对，并能回到原邮件查找材料。

- 缺字段、有值但格式错误、交通类发票缺行程单、类别冲突、同票关系或匹配未决、下载／转换失败分别说明原因。
- 页面按邮件归并：一封邮件一条邮件级提示，显示邮件名、时间，文件及原因放在详情。空主题或不可用时间使用明确占位，不用处理时间替代邮件时间。
- 页面展示已有文件标识与原因；不承诺逐项展示来源字段值或候选金额对照，详细证据结合 JSON 与原邮件核对。收集异常可能只能定位到邮件。
- 已提取、格式检查通过不等于真伪验证。完整提示条件及文案见[已审核文案表](T3前端提示文案表_已审核.md)。

### US-10 统一下载与失败状态

- 本机和云端每轮均在独立临时目录处理，页面只提供本轮 ZIP 下载，。
- ZIP 包含汇总表、JSON 和选定的发票／行程单 PDF；不含 XML、图片原件、OFD、原始 ZIP、内部目录或日志。没有可交付 PDF 时不虚构文件。
- 下载按钮出现前完成交付内容检查；汇总表未生成时停止打包，显示汇总失败；表已生成但打包或内容检查失败时显示下载包失败，不显示下载按钮，两种失败互斥。
- 按临时目录规则清理工作文件。页面和日志不展示 API Key；签名下载链接不在页面、JSON 或日志中暴露完整参数。

## 六、非功能要求与交付约束

| 维度 | 产品要求 | 核对方法 |
|---|---|---|
| 来源可追溯 | JSON 保存邮件定位、完整原名、来源序号及交付名映射 | 从业务记录反查同邮件文件，核对导出映射；来源字段本身不证明文件真实性 |
| 数据隔离 | 一文件一提取结果，一发票一笔；每轮独立目录 | 多文件、多邮件及连续两轮检查，不串字段、不混入旧结果 |
| 容错 | 记录已取得信息和具体错误，不将已知失败显示为完成 | 分别验证文件、服务、汇总表和交付包失败路径 |
| 配置与保密 | 密钥从环境／本地配置取得；业务输出不含密钥及内部目录 | 检查页面、JSON、ZIP 和日志；模型配置见 README |
| 重复运行 | 不自动标已读，不做跨轮去重 | 重复处理同批未读邮件可能再次输出，不能承诺跨轮只处理一次 |

具体接口、资源限额、安全存盘和算法约束见重构方案与对应规格。技术组件与目录说明由架构文档维护，PRD 不另列一套接口清单。
