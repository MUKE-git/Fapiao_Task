## 每条待核结果的固定定位区

产品负责人 2026-10-21 确认：页面按邮件归并待核提示，**一封邮件只显示一条邮件级提示**。该提示包含邮件主题、可用的邮件时间和需要用户处理的事项摘要；同一邮件的多个文件或字段原因放在这条提示的详情内，不重复显示邮件标题，也不丢弃底层 JSON 中的逐文件、逐字段原因。已由可用 PDF 得到完整结果时，与业务结果无关的技术登记信息不单独要求用户核对；真正影响结果的格式错误、冲突或缺凭证仍需显示。

对每封有待核事项的邮件显示以下现有信息，用户可据此回到邮箱找原件：

| 页面标签 | 内容与缺失处理 |
|---|---|
| 邮件主题 | 完整解码主题；空值显示“（无主题）”。页面可折行，允许复制全文。 |
| 邮件时间 | 使用现有邮件日期字段，显示 `YYYY-MM-DD HH:mm`；无法取得时显示“（邮件时间不可用）”。不能以处理时间冒充邮件时间。 |
| 相关文件 | 文件原名及本轮文件编号；多个来源逐个列出。用户可按邮件主题和邮件时间定位，再核对附件。 |

现有 `mail_uid` 保留为内部追源锚点，不要求用户在网页邮箱输入 UID。本阶段不新增发件人字段。下载链接若含签名/令牌，页面只显示链接所在邮件和下载结果，不展示完整链接参数。

同一邮件可有多条原因，但页面以**邮件卡片 → 具体发票/文件 → 原因**组织，避免反复显示相同主题。某字段从 XML 等来源提取成功但尚未做真伪校验时，页面只说“已提取”，不说“已验证”。页面不声称用户能在下载包内找到未交付的原格式文件；需查看原件时引导用户到原邮件。

### P07～P10、P26 的触发边界

- **P07 XML**：字节不完整或 XML 语法不成立属于文件本身异常；XML 可正常打开但缺少项目需要的节点，也可能只是模板不同或字段确实未填，不能说文件“坏了”。仅缺部分字段时保留已取得的值。当前 `pipeline.py::_file_issue_for_page` 将 XML 错误映射为上述概括提示，`app_demo.py::_render_mail_alerts` 显示邮件定位信息、已有文件标识和原因；未实现原要求的已提取／未提取字段对照展示。JSON 中保存字段不等于页面展示了字段对照，该项展示要求尚未满足。
- **P08**：当前不用于 OFD 输入；OFD 在登记前忽略。
- **P09 图片**：按当前 `pipeline.py::_file_issue_for_page` 的分支顺序，图片读取失败优先使用 P06，`MODEL_FIELD_MISSING` 优先使用 P17，其他模型错误优先使用 P22；其余 `IMAGE_` 或 `MULTIPLE_DOCUMENTS_` 原因使用 P09，包括图片 PDF 副本生成失败。页面显示上述概括文案和已有文件标识，不逐项列出未提取字段，也不能一概归因于用户拍摄质量。
- **P10 凭证类别**：比较的是 **Invoice 发票 / Itinerary 行程单 / Unknown 无法判断**，不是 PDF/XML 等物理格式。PDF 链先从附件原名关键词推断（“行程单”优先于“发票”），再从 PDF 正文关键词粗分；原名有明确关键词时优先形成本机预读类型，AI 的 `file_classifications` 逐文件给出另一份分类。例如原名为“行程单.pdf”、正文及 AI 均判断为发票，就会出现分歧。2026-10-21 实测曾发现正文预读为 `Unknown`、原名与 AI 均为 `Itinerary` 时被误报；当前代码已改为只有明确的 `Invoice` 与 `Itinerary` 相反才触发该提示。T3-1/T3-2 联调仍须保证同一文件只给一次 P10 提示，详情显示文件标识和核查原因，不逐项展示文件名、内容和模型各自的判断结果。
- **P25/P26 先后关系**：汇总表未生成时显示 P25，停止进入打包流程；汇总表已生成，随后制作 ZIP 或核对包内 Excel、JSON、应交付 PDF 失败时显示 P26。同一失败不同时显示两条。
- **P26 下载包**：T3-8 在页面显示下载按钮之前生成并核查 ZIP；T3-9 将成功或失败状态交给页面。T3-1 只在收到“交付包已核查”及现成 ZIP 时显示按钮；收到打包失败时显示 P26 且不展示按钮。用户尚未点击下载，所以不写“重试下载”。浏览器点击后的传输失败是另一种情况，不能冒充 P26 的触发条件。本机和云端运行均使用同一下载行为。
