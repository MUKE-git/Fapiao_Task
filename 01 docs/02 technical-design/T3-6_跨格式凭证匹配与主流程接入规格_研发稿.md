# T3-6 跨格式凭证匹配与主流程接入规格（研发稿）

日期：2026-10-15。归属《计划分工》T3-6，对应最终图 N→O、X→Y、O⇢U/Q 及候选汇总后通向 MATCH→DEDUP→CHECK→ELIG→WRITE/SKIP 的整链。这里匹配的是**同一张发票的 XML、PDF、OFD、图片来源**；发票与行程单配对仍由 T2-3 负责，不能混成同一种匹配。规划按 T2 已完成衔接，实际接入须核对 T2 代码与测试状态。

## 1. 输入、输出和稳定编号

- 输入为同一封邮件内已登记的全部文件级 `DocumentResult`，包括角色为 `Invoice`、`Itinerary`、`Unknown` 的结果；无处理器或处理失败的文件仍保留 `FileRecord` 和错误提示。链接下载、直接附件和 ZIP 解出文件在登记后走同一入口。公共附件链先做**同邮件内容 MD5 去重**；本任务不再次按文件名删文件。
- 当前端口 `StagePorts.combine_vouchers(mail, results) -> list[DocumentResult]` 可作为接入点。**已确认同票且字段无冲突**时输出一张发票一个候选；同号却有未解决的关键字段冲突且无可靠 XML 值时，暂时保留多个独立候选给 T2-4 仲裁，不能在这里强行合成一条。`Itinerary` 先经本节第 3 节的多格式重复判定，再供 T2-3 匹配；`Unknown` 保留供页面提示；不从输出消失一个尚未解决的来源。
- 合并后候选的 `source_file_seq` 列出全部已确认同票来源，每个序号仍可从 `mail.files` 反查到原名和邮件。`file_seq` 作为记录锚点：有有效 XML 时选其序号；否则选已确认原始 PDF、OFD、图片中登记序号最小者。锚点与 `record_id=mail_id-file_seq` 保持一致。冲突未合并时，**各候选各用自己的来源文件序号和不同 `record_id`**；不得将一份文件同时宣称为两条已确认记录的来源，也不得给不同记录复用同一 `record_id`。
- 字段值、原始值、来源格式、`file_seq`、证据位置、冲突及“为何合并/未合并”须留在调试结果中。当前 `DocumentResult` 和 `task_debug.json` 只含聚合来源列表，没有字段级证据与冲突明细；研发以兼容方式扩展，不更改既有字段意义，保持 JSON/Excel 八列及固定用例基线。

## 2. 自动同票决策表

所有自动关系只在**同一邮件**内判断；跨邮件同号交给 T2-4 本轮去重仲裁。号码须先满足已确认的 20 位数字规则。日期、金额按规范值比较，金额用 `Decimal` 且不提前四舍五入两位。原文件名和附件顺序都不能单独证明同票。

| 输入关系 | 决策 | 结果和待核边界 |
|---|---|---|
| 两来源有效票号相同，其他字段不冲突 | 自动同票 | 合成一个发票候选，合并来源；非空字段互补。 |
| 两来源有效票号不同 | 不同票 | 保留两笔；即使日期、金额、销售方相同也不合并。 |
| 一方票号缺失，另一方有效 | 仅在缺号来源与有号来源的**日期、价税合计、销售方三项均有效且一致**，且该有号来源是唯一候选时自动归并 | 任一锚点缺失/无效、出现反证或存在多个候选时不归并；标待核并列出候选，不以“最近金额”或文件顺序选一项。 |
| 两方票号都缺失 | 不自动认定同票 | 各自保留候选并待核；相同日期/金额/销售方仍可能是两张票。 |
| 相同有效票号，但 XML 与凭证字段相反 | 关系可确认为同票，字段有冲突 | 有效 XML 字段作为业务值，原凭证值与差异留痕；记录待核，不能把冲突说成验证通过。 |
| 相同有效票号，无 XML，PDF/OFD/图片字段相反 | 关系为同号候选，不能静默合成“无冲突”记录 | 各自保留独立 `record_id` 与来源，送本轮去重仲裁的无 XML 分支；模型不能确认时人工待核。 |
| 同票号的多份凭证，关键业务信息一致 | 字节相同先由 MD5 去重；字节不同但票号及关键业务信息一致、均通过检查时，也可确认同票并合并全部来源 | 邮件附件和下载件可能只是同票的不同 PDF 版本；这属于重复来源。交付时 T3-1 只选一份可用 PDF，其他来源保留在 JSON。 |
| 一份无号凭证可落到多张发票 | 不自动分配 | 保留未决来源和待核提示，不让该凭证同时“证实”多张票。 |
| XML/PDF 匹配失败或角色 Unknown | 落单回流 | XML 独立发票候选进入“仅 XML/缺凭证”；PDF 按纯 PDF 提取候选继续；Unknown 保留文件登记和提示，不造发票。 |

上述缺号规则是技术侧的**保守自动化门槛**：宁可留下待核，也不以弱证据把两张票合成一张。若实际样本显示此门槛仍有误合并风险，研发应收紧并提供具体反例，不自行放宽。

## 3. 合并字段和来源优先级

1. 对每个字段先排除缺失、格式错误和无证据候选；XML **有效结构化值**优先。XML 自身同字段多值冲突时不得把它当可靠优先值，应保留冲突并待核。
2. XML 对某字段缺失或无效时，可用同票 PDF/OFD/图片的唯一可靠值补空，并标明补值来源；不能把另一文件的值写回 XML 原文件证据。无 XML 时，多来源值一致则采用；有明确分歧则交仲裁/待核，不以“PDF 总是高于 OFD”覆盖不同业务值。
3. 发票候选的 `travel_time`、`origin_dest` 始终不从发票 XML/PDF/OFD/图片中猜值；仅 T2-3 唯一匹配的行程单汇入 a 类发票。同一行程单的 PDF/OFD/图片可能字节不同：若转换链能证明来自同一原文件，或均带有一致且唯一的行程单业务编号且全部关键字段无冲突，可合为一个**逻辑行程单**，并保留每个来源文件；不能只凭金额、日期或相似文件名认定重复。无法确认是否重复的多份行程单须标待核，**不能作为 T2-3 的“只剩一票一单”自动匹配条件**，也不能同时给同一发票重复配对。现有 `ItineraryRecord` 只有单一 `record_id`，研发须加法扩展来源/重复组和匹配门槛，不改已审核 T2-3 预期。
4. 最终 JSON 保留所有 `files[]`、聚合 `source_file_seq`、每个字段来源与冲突原因；用户 Excel 仍只写八列。T3-1 的 PDF 选择独立于字段权威性：XML 可提供业务值，但 XML 不出现在 ZIP；有原始 PDF 优先交付原始 PDF。同级多个已确认同票 PDF 依登记顺序选一份；业务值冲突且未决时不随意交付某份 PDF。
5. **跨邮件同号也必须启用 XML 优先分支。**同一轮结果进入 T2-4 后，若冲突组中有与该票号一致、字段有效且无内部矛盾的 XML 来源，按《重构方案》§4.3 以 XML 的有效字段为准，保留其余候选和差异证据，不调用“无 XML”的二次 AI 仲裁。若多个 XML 自身相互冲突，不能任选其一，进入人工待核。当前 `dedup_arbitrator.py::_choose_with_ai` 默认只加载 PDF 文本，尚未实现此分支；研发须在 T2-4 接口处接入 XML 证据，且只在**无可靠 XML**时走二次仲裁。OFD/图片造成的无 XML 冲突，需给仲裁器提供可核查的原文证据；取不到证据时直接保留未决，不把 PDF 专用读取失败误作已确认。

## 4. 接口示例与主流程顺序

同封邮件 A 组三文件示意（值来自用户样本，非当前程序输出）：

```text
输入：
  file_seq=01 XML Invoice  no=26447000000342589935 date=2026-04-27 amount=121.74
  file_seq=02 PDF Invoice  no=26447000000342589935 date=2026-04-27 amount=121.74
  file_seq=03 OFD Invoice  no=26447000000342589935 date=2026-04-27 amount=121.74
输出：
  1 个 Invoice 候选；file_seq=01；source_file_seq=[01,02,03]
  record_id=MsgN-01；字段值与每字段来源、同票证据写入 JSON
  T3-1 交付选 file_seq=02 的原始 PDF，01/03 的 exported_name 为空
```

主流程顺序固定为：登记/去重 → PDF/XML/OFD/图片逐文件处理 → **本任务同票归并与落单回流** → 保存全部行程单 → T2-3 发票↔行程单匹配 → T2-4 本轮票号去重仲裁（含无 XML 二次仲裁）→ T2-6 字段校验 → 全缺筛选 → Excel/JSON → T3-1 交付 PDF/ZIP。不得先入 Excel 再补来源、先删除未决文件，或让格式处理器各自写表。

同一邮件若 PDF `Msg1-02` 与 OFD `Msg1-03` 都识别出票号 `26447000000342589935`，但金额分别为 `121.74` 和 `131.74`、且无 XML：先生成两个不同 `record_id` 的候选，各挂自己的来源；T2-4 如能依据两份可核查原文确认其一，另一条仅从 Excel 跳过而仍留 JSON；不能确认时两条都保留为人工待核，按既定全缺筛选规则决定是否入 Excel，用户票据不任意选一份。若两份金额同为 `121.74` 且其他关键字段也一致，则合成一个候选，来源同时保留，交付优先选可用原始 PDF。

当前 `pipeline.py::process_message` 在 `combine_vouchers` 后才创建发票/行程单记录，位置可用；但 `DocumentResult` 只承载单份扁平字段，`data_model.py` 尚无字段级冲突证据，`pipeline.py` 的未知类型提示还写作“PDF 类型无法确定”。研发需协调端口与 JSON 的加法扩展，并保持已有固定用例、来源链检查和导出名映射可用。一文件包含多张独立票据时，不得悄悄只取一张；若当前接口无法承载多候选，明确标人工待核并留样本给后续契约增量。

## 5. 交接与验收证据

研发交接逐格覆盖上表：A/C 两组同票三格式、B 图异票、缺号唯一/多候选、同号字段冲突有/无 XML、**跨邮件**同号冲突有 XML、多个 XML 冲突、XML 落单、PDF 落单、链接+附件同内容 MD5、字节不同但业务值一致的两份 PDF、多票争一凭证、同一行程单多格式重复及无法确认重复。每格提供输入文件关系、程序决策、JSON 来源/冲突、Excel 行数与值、用户 PDF 清单及页面提示。测试工程师独立制定新增预期并区分受控端口测试与整链真实处理；原有 18 条已审核必选用例不因本规格重编号或改预期。
