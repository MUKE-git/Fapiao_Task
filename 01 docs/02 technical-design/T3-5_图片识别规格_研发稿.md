# T3-5 图片识别规格（研发稿）

日期：2026-10-15。归属《计划分工》T3-5，对应最终图 V/W→X、X→Y 和图片识别为行程单时的 X⇢I。图片是识别输入；用户交付按 T3-1 只给发票或行程单 PDF，不直接给图片。本稿不表示图片处理器已实现或模型结果已验证。

## 1. 输入登记与真实格式

- 公共附件链先登记 `file_seq`、原名、邮件定位及内容摘要，再依据文件头和解码器识别真实图片格式；扩展名不是决定依据。用户样本 `发票文件1.png` 实际可按 JPEG 解码，不能仅因 `.png` 与内容不同就丢弃，也不能把原名改写成 `.jpg`。
- 处理 EXIF 方向，限制文件字节、像素、帧数及解码耗时；损坏、加密、超限或不支持的图像保留登记并明确提示，不能调用模型后把异常当作“字段缺失”。多帧图像逐帧检查，避免漏页；来源仍指向原文件。
- 单图片输入 T3-2 多模态适配，模型返回文件级候选和 `Invoice` / `Itinerary` / `Unknown` 角色；本地硬规则再校验。若画面有多张独立票据，不能任取第一张并宣称处理完成；需保留多区域来源并由主流程承载多候选，无法可靠拆分时人工待核。

## 2. 发票图片字段与本地硬规则

| 字段 | 候选来源 | 硬规则与处理 |
|---|---|---|
| 发票号码 | 票面可见文字/多模态输出 | 必须为已确认的 20 位数字；模糊或不满足规则时不采信，保留原候选及待核原因。 |
| 开票日期 | 票面“开票日期”附近 | 有效日期，统一 `YYYY-MM-DD`；不得用邮件日期、图片创建时间或行程日期代替。 |
| 报销金额 | 票面“价税合计（小写）” | 十进制、>0、最多四位小数；不能把未税合计、税额或单价当作报销金额。若两个显式价税合计冲突则待核。 |
| 发票类型、票面类型、销售方 | 票面标题、项目和销售方区域 | 票面类型按既有 `*一级*二级` 规则取值；销售方不能误用购买方；发票类型缺失允许留空。 |

本地规则只证明候选符合已确认的格式和来源条件，不证明发票真实或图片未经修改。无法读出字段、候选不满足规则、模型服务失败分别记录；能确认的其他字段仍保留。样本 B 图号码 `26522000000868668241`、日期 `2026-08-24`、价税合计 `21.60`，未税 `21.39`；它与本地 A 组及正文链接 C 组均不同票，不得作为同票配对正例。

## 3. 行程单图片分流

图片若明确是行程单，提取并保存 `record_id`（程序分配）、`match_amount`、首笔 `travel_time`、首段 `origin_dest`；不提取或要求行程单企业名称。其角色和四字段先进入全部 `itineraries`，包含未匹配项；现有行程单匹配器再决定是否汇入 a 类发票。图片上同时出现“发票”“行程单”字样而角色无法确定时，不因关键词强行当发票；明确分类相反触发 P10，无法判断单独待核。

## 4. 跨格式与 PDF 交付

- 图片形成的发票候选由 T3-6 与 XML/PDF/OFD 按同票证据配对；同票合并成一笔，异票保留各自记录。图片字段不能静默覆盖有效 XML 值；缺号或一图多票时遵守 T3-6 的不确定性规则。
- 同票已有可用原始 PDF 或 OFD 转 PDF 时，图片不再重复交付；仅有可用图片时，把**完整画面按比例**排版为 PDF，处理旋转和页边界，核对 PDF 可打开、页数/帧数、关键文字及二维码区域未裁切。不能通过改扩展名伪造 PDF。
- 转换后的 PDF 只作为图片来源的交付副本；原始图片不进入 ZIP。`task_debug.json` 保留原名、真实格式、来源文件序号、转换状态和 `exported_name`。转换失败时若已提取字段，仍保留记录与 P09/转换失败原因，但不交付坏 PDF。

## 5. 研发交接与验证材料

提供用户 B 图的真实格式识别和字段预期，并补齐清晰发票、模糊/遮挡、旋转、错误扩展名、超限/损坏、行程单、多票同图、仅图片、图片+XML 同票与异票样本。分别验证模型候选、本地规则判定、`DocumentResult`、行程单列表、跨格式关系、PDF 交付与前端 P06/P09/P10/P13/P14。受控模型输出只能证明程序如何处理给定候选；真实多模态调用与最终人工样本核对另行报告。
