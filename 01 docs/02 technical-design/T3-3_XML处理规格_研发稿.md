# T3-3 XML 处理规格（研发稿）

日期：2026-10-15。归属《计划分工》T3-3。依据《重构方案》最终图 M→N→O、仅 XML 的 U→Z 及用户样本核查草案。以下为研发实现契约，不表示项目解析器已运行。XML 是结构化**数据来源**；只有 XML 时可形成发票记录，但缺少可交付的票面凭证 PDF。

## 1. 输入、安全与文件级输出

- 从公共附件链取得已登记的单个 XML 文件，沿用同邮件 MD5 去重、`mail_id`、`file_seq`、`original_name` 和内部存盘名。内容判断以实际字节/结构为准，扩展名只作线索；XML 不直接写 Excel 或改文件名。
- 限制文件大小、解析深度和节点数；拒绝 DTD、外部实体、网络实体和路径引用，避免从 XML 读取本地文件或触发外部请求。编码按 XML 声明读取，无法解析时保留文件登记并给出错误原因，其他文件继续处理。
- 输出 `DocumentResult(file_seq=本文件序号, role=Invoice|Unknown, fields=..., source_file_seq=[本文件序号], error_reason=...)`。字段及其 XPath/原始值的证据必须可供 T3-6 核对；精确承载方式由研发与数据模型协同决定，不得丢掉已有 `files[]` 来源关系。

## 2. 已核实样本 A 的字段映射

下表只确认 `T3出行电子发票(XML)A.xml` 的 `EInvoice` 模板；其他模板走显式映射或“暂不支持/待核”，不得把以下 XPath 猜套到所有 XML。目标字段按 PRD 八列和现有 `InvoiceFields`。

| 目标字段 | A 样本 XPath（省略根 `/EInvoice`） | 值与规则 |
|---|---|---|
| 发票号码 | `/TaxSupervisionInfo/InvoiceNumber`；交叉核对 `/Header/EIid` | 两者均为 `26447000000342589935`。存在多个非空值且不一致时标冲突，不能任选其一。 |
| 发票日期 | `/TaxSupervisionInfo/IssueTime` | `2026-04-27`；只接受可解析的有效日期，规范成 `YYYY-MM-DD`。`RequestTime` 是请求时间，不代替开票日期。 |
| 报销金额 | `/EInvoiceData/BasicInformation/TotalTax-includedAmount` | `121.74`，按 `Decimal` 读取并保留最多四位精度；不可把未税金额 `118.19` 或税额 `3.55` 当价税合计。 |
| 发票类型 | `/Header/InherentLabel/EInvoiceType/LabelName` 与 `/Header/InherentLabel/GeneralOrSpecialVAT/LabelName` | 样本分别是“电子发票”“普通发票”；组合/规范化沿用已确认的发票类型规则。缺失可留空，不从文件名猜测。 |
| 票面类型 | `/EInvoiceData/IssuItemInformation/ItemName` | 样本为 `*运输服务*客运服务费`；按既有规则取二级“客运服务费”，用它判 a/b 类。多项目时保留全部原值；若无法唯一形成票面类型则待核，不任取第一项。 |
| 销售方 | `/EInvoiceData/SellerInformation/SellerName` | “南京领行科技股份有限公司广州分公司”；不得误取购买方。 |
| 出行时间、出发地/目的地 | 本发票 XML 无行程单字段 | 留空；只有匹配的行程单可以汇入 a 类发票，不从开票日期或空表头推断。 |

可额外读取税额、未税额、购买方等用于交叉核查，但不增加用户 Excel 列。每个字段保存原始 XML 文本、规范值和 XPath 证据；缺节点、空文本、重复且冲突、有值但格式错分别标明，不合并成一个“解析失败”。

## 3. 与凭证匹配及主流程的边界

1. XML 语法可解析且**确认是发票结构**时形成文件级发票候选；T3-6 再用完整票号及其他可靠证据与 PDF/OFD/图片凭证匹配。跨格式同票关系不可由 XML 处理器自行猜测。有效 XML 值在已确认的同票合并中优先；与视觉凭证冲突要显式留痕并待核，不静默覆盖。
2. 匹配后有 PDF/OFD/图片票面来源时由 T3-8 选择并交付 PDF；只有 XML、没有票面凭证时仍保留候选及来源，标“缺凭证”，由 T3-1 显示 P12。**不从 XML 生成仿造票面 PDF**，也不把 XML 放入用户下载包。
3. XML 候选和其他来源进入统一的发票↔行程单匹配、本轮票号去重、字段校验及入表筛选。票号、日期、金额全缺才排除 Excel；排除也必须保留 JSON 来源和原因。仅 XML 不等于自动排除 Excel。
4. XML 无法解析、非发票 XML 或模板不支持时仍保留 `FileRecord` 和可定位的原邮件信息，给出 P06/P07/P11 中与实际原因对应的提示；不能制造一笔空发票记录冒充成功提取。

## 4. 研发交接与验证材料

- 为 A 样本和用户提供的链接 XML 各建立“原 XPath → 规范字段 → JSON/Excel 目标值”独立预期；链接当次可下载不保证以后仍有效，离线测试应固定脱敏副本或受控响应。样本中无原邮件头，不能编造邮件主题/时间。
- 覆盖：正常单项目、多项目、缺一个字段、金额小数四位、号码两处冲突、非法日期、空节点、错误编码、截断 XML、DTD/外部实体、超限文件、仅 XML、有同票 PDF、异票 PDF。每项分别检查文件登记、候选、来源证据、错误、JSON/Excel 与前端提示。
- 清楚标注“解析器单测”“主流程受控联调”“真实邮件联调”的结果；通过前者不能宣称下载包或全流程已验收。测试标准答案按已确认业务规则独立制定，不从程序输出反推。
