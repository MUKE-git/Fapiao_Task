# T3-9 主流程接入规格（研发稿）

日期：2026-10-21。T3-9 只负责**把既有 T2 流程与 T3-2～T3-7 的结果接成最终流程图，并把本轮结果交给 T3-8**。它不重新实现 XML/OFD/图片提取、正文链接下载、跨格式同票判断、发票与行程单匹配、模型适配、PDF 业务命名或页面提示。规划假定 T2 已完成并通过测试；实际接线时由研发核对代码和交接状态。

## 调用顺序与归属

| 顺序 | 输入与动作 | 规则所有者；T3-9 只做的事 |
|---|---|---|
| 1 | 每轮创建独立临时工作目录；获取邮件，汇入直接附件、ZIP 解出文件和正文链接文件；统一登记、编号、MD5 去重 | T2 公共附件链与 T3-7；本任务接线和管理本轮工作目录，不重写下载器或去重器。 |
| 2 | 对每个真实格式文件调用 PDF、XML、OFD、图片处理器，保留失败与 Unknown 文件 | T2 PDF、T3-2～T3-5；本任务调度并保证一文件失败不吞掉同邮件其他结果。 |
| 3 | 合并同票多格式来源、保留冲突候选、落单 XML/PDF 回流；保存全部行程单 | T3-6；本任务消费其结果并保留每个来源、字段证据及待核原因。 |
| 4 | 发票与行程单匹配、本轮同号去重仲裁、字段校验、全缺入表筛选 | T2-3/T2-4/T2-6 与《重构方案》；本任务调用并把 T3 的 XML/OFD/图片证据传入，不能绕过或复制一套规则。 |
| 5 | 统一写本轮八列 Excel、最终 JSON，再生成用户交付包 | 既有写表/序列化模块与 T3-8；本任务保证顺序、结果身份和失败状态传递。 |

跨邮件同号冲突必须在第 4 步识别可靠 XML 来源：有效 XML 字段优先，原候选和差异证据留在 JSON；多个 XML 相互冲突则人工待核；无可靠 XML 才可调用 T2-4 的二次 AI 仲裁。当前 `dedup_arbitrator.py::_choose_with_ai` 主要读取 PDF 文本，T3-9 须把 XML 来源和 OFD/图片可核查证据接入仲裁器；证据取不到时维持未决，不把读取失败当作已确认。

本轮 JSON 应保留全部 `files[]`、全部行程单、发票记录、聚合来源、字段来源与冲突、未入表原因。T3-9 负责结果契约的加法扩展及调用次序，保持已审核 T2 用例和现有八列语义。`pipeline.py` 的未知文件提示若仍写“PDF 类型无法确定”，应按实际文件类型产生结构化原因，具体页面文案由 T3-1 展示。

## 与前端及交付包的接口

T3-8 接收本轮已完成的业务结果、可交付 PDF 候选及工作目录，返回 ZIP 或明确的打包/检查失败状态。T3-9 在汇总表失败时停止打包，向前端提供 P25 所需状态；汇总表已成功但 T3-8 失败时提供 P26 所需状态。T3-1 只读取这些结构化状态和已核查 ZIP，不生成文件或从提示文字反推业务结果。无论本机或云端运行，都不回退到桌面输出模式；本轮临时工作文件与交付文件分离并按既定生命周期清理。

## 交接与验收证据

研发逐节点对照《T3最终流程覆盖与开发分工_规划稿.md》的最终图，给出附件、纯链接、附件加链接、仅 XML、仅 OFD、仅图片、XML 加 PDF/OFD/图片、落单 XML/PDF、图片行程单、Unknown、跨邮件 XML 冲突等整链运行记录。每项核对实际调用了哪个模块、JSON 来源和原因、Excel 行和值、T3-8 ZIP 清单以及 T3-1 状态。受控端口联调与真实格式/真实模型/真实链接联调分开报告；本任务接线通过不等于各处理器单独验收通过，独立测试由测试工程师负责。
