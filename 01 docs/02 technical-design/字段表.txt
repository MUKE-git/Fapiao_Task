3.1 业务背景
发票邮件处理系统：通过 IMAP 收取财务邮箱里的发票/行程单邮件，识别 PDF/XML/OFD/图片凭证，逐条提取字段，按「一发票一笔」落成结构化记录，输出员工报销 Excel 汇总表；对缺凭证、字段缺失、重复、匹配失败等异常打 status 标记并引导前端人工核查。记录单位 = 一发票一笔；行程单不单独成行，匹配后字段汇入 a 类发票。

3.4 业务规则

- 发票必填：日期、号码、金额、票面类型、销售方；缺失标记，有值查规则。发票类型非必填，缺失留空，有值查规则。
- a/b 根据有效票面类型命中 TRANSPORT_RECEIPT_KEYWORDS 判定；对“费”字容错。票面类型缺失/无效时分类暂空并人工待核，不能默认 b 类。
- b 类不校验旅行字段；a 类校验时间与起终点是否从行程单汇入。
- 行程单仅四字段：record_id、match_amount、travel_time、origin_dest，全部持久保存在每封邮件的 itineraries 数组中，包括未匹配项。不保存或提取企业名称。
- 单邮件恰好一票一单自动成组，不要求金额一致或完整；其他数量组合按金额→完整解码原名匹配，不能唯一确定则人工待核。单对单也遵守 a 类汇入及入表规则。
- 金额最多四位，JSON 用十进制字符串保留原始位数，计算使用 Decimal/ROUND_HALF_UP；先按较低精度比较，再用原始差值 ≤0.5 判断候选。不得提前舍入两位，Excel 显示两位。超四位或非法值提示核查。
- 按发票入表，仅票号、日期、金额全部缺失才排除，前端提醒且 JSON 保留；部分缺失仍入表并核查。
- 同邮件 MD5 去重复附件；本轮同票号去重仲裁：一致保留一条，不一致 XML 优先（T3），否则 AI 二次仲裁或人工待核。空票号不作为共同票号合并，不查历史文件。
- 用户 Excel 固定八列，行程单只汇入时间与起终点，不另建表、不追加独立行。内部校验表沿用现有布局并删除行程单企业名称列。
- 本轮编号可在下一轮重新开始，每轮使用独立输出目录。
- files 的 internal_name 与 exported_name 保存内部名、用户导出名对应；导出前 exported_name 可空。完整实际文件名最多120字符，含编号/扩展名/重名后缀，超长主体截断加短摘要；original_name 完整保留。
- 单次 AI 输入一个文件，file_classifications 只返回对应的一项；匹配由程序完成。

3.5 JSON 结构及样例

完整 JSON 样例以 ../01 project/重构方案.md 的 §3.3 为唯一维护源，避免重复示例更新不同步。
每封邮件包含 files、itineraries、records、dedup_skipped、error_reason 等字段；行程单数组中的 record_id 与文件编号对应。records.matched_itinerary 引用对应 file_seq，match_amount 与行程单条目一致。
未匹配行程单仍保存四字段；b 类无 matched_itinerary，旅行列留空。缺失/无效票面类型 kind 暂空、status=人工待核。
发票可选 invoice_type 缺失用空字符串；必填缺失占位与格式错误分别标记；缺失原因须可追溯到记录。
